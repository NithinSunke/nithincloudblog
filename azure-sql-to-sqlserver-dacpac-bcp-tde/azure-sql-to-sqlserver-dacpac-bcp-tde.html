Azure SQL Database to SQL Server (VM) with DACPAC, BCP and TDE

Nithin Sunke · November 2, 2026 · 15 min read

Lab 6 of the Azure SQL Database migration series. This time the schema and data travel separately: a DACPAC creates the empty database, TDE is switched on before a single row lands, and BCP loads the data straight into encrypted pages. It covers both a SQL Server-generated certificate and a customer-provided one.

How it works, and why TDE goes first

Azure SQL DB (TDE) ──Extract──▶ scsbank_azure.dacpac ──Publish──▶ MSSQLSRV01/scsbank_bcp_back (empty)
                                                                     └─ enable TDE (empty → instant)
Azure SQL DB ──bcp out──▶ B:\Lab6\data\*.dat (NOT encrypted) ──bcp in──▶ pages encrypted on write

Like Lab 3 in reverse: a DACPAC (schema only, like expdp CONTENT=METADATA_ONLY) builds the empty database, and BCP moves the data table by table (like CONTENT=DATA_ONLY or SQL*Loader).

StageEncrypted?
Azure sourceYes: TDE, service-managed key
In transit (SqlPackage, bcp)Yes: TLS
.dacpac and .dat files on diskNo. Protect them and delete them.
Target databaseYes, from the first row, because TDE is enabled before loading

With BACPAC (Lab 5), the import creates the database, so you can only enable TDE afterwards. The data then sits unencrypted until a background scan rewrites every page. With DACPAC + BCP you control when the database is created, so you can encrypt it while it's still empty.

Prepare folders and the session

In an Administrator PowerShell:

mkdir B:\Lab6\data, B:\Lab6\logs
icacls "B:\Lab6" /inheritance:r /grant:r "Administrators:(OI)(CI)F" "${env:USERNAME}:(OI)(CI)F" "SYSTEM:(OI)(CI)F"

# Folder for TDE key backups (written by the SQL Server service account)
mkdir B:\Keys -Force
icacls "B:\Keys" /inheritance:r /grant:r "Administrators:(OI)(CI)F" "SYSTEM:(OI)(CI)F" "NT Service\MSSQLSERVER:(OI)(CI)M"

# Azure session with a hidden password, then wake the serverless DB
$az = "tcp:cisql01.database.windows.net,1433"; $azdb = "scsbank"; $user = "nsunke"
$sec = Read-Host "Azure SQL password" -AsSecureString
$pwd = [Runtime.InteropServices.Marshal]::PtrToStringAuto(
         [Runtime.InteropServices.Marshal]::SecureStringToBSTR($sec))
sqlcmd -S $az -d $azdb -U $user -P $pwd -l 120 -Q "SELECT 1" | Out-Null
  • Use ${env:USERNAME}, not $env:USERNAME:. PowerShell reads the colon as part of the variable name, and icacls then fails with Invalid parameter.
  • NT Service\MSSQLSERVER needs Modify on B:\Keys, because certificate backups are written by the SQL Server service, not by your login.
  • The free-tier database auto-pauses after 15 idle minutes. The warm-up query avoids the login timeouts that broke three tables in Lab 3.

Check TDE on the source and record a baseline

On cisql01/scsbank:

SELECT name, is_encrypted FROM sys.databases WHERE name = 'scsbank';          -- 1
SELECT DB_NAME(database_id) db, encryption_state_desc, key_algorithm, key_length, encryptor_type
FROM sys.dm_database_encryption_keys;                                           -- ENCRYPTED, AES 256

SELECT s.name, t.name, SUM(p.rows) AS row_count
FROM sys.tables t JOIN sys.schemas s ON t.schema_id = s.schema_id
JOIN sys.partitions p ON t.object_id = p.object_id AND p.index_id IN (0,1)
GROUP BY s.name, t.name ORDER BY 1,2;
SELECT type_desc, COUNT(*) FROM sys.objects WHERE is_ms_shipped = 0 GROUP BY type_desc ORDER BY 1;
SELECT SUM(Balance) AS total_balance FROM Account.Account;

Save these results. They're the target you'll compare against at the end. In the portal, the same TDE status is under SQL database → Security → Data Encryption.

Move the schema (DACPAC)

1Extract the schema only from Azure

sqlpackage /Action:Extract `
  /SourceServerName:cisql01.database.windows.net /SourceDatabaseName:scsbank `
  /SourceUser:$user /SourcePassword:$pwd /SourceTimeout:120 `
  /TargetFile:"B:\Lab6\scsbank_azure.dacpac" `
  /p:ExtractAllTableData=False /p:IgnoreUserLoginMappings=True /p:IgnorePermissions=True

Users and permissions are left out. Azure contained users don't map cleanly to an on-premises server, so you recreate application logins yourself.

2Publish to SQL Server

sqlpackage /Action:Publish `
  /SourceFile:"B:\Lab6\scsbank_azure.dacpac" `
  /TargetServerName:MSSQLSRV01 /TargetDatabaseName:scsbank_bcp_back `
  /TargetTrustServerCertificate:True `
  /p:AllowIncompatiblePlatform=True `
  /p:ExcludeObjectTypes="Users;Logins;RoleMembership;Permissions;DatabaseScopedCredentials" `
  /p:BlockOnPossibleDataLoss=True
  • AllowIncompatiblePlatform: the DACPAC is stamped for Azure SQL Database. This is the mirror image of the SQL Server 2025 → Azure error in Lab 3.
  • TargetTrustServerCertificate: only while the VM has a self-signed TLS certificate.

3Confirm: empty, and not encrypted

SELECT name, is_encrypted FROM sys.databases WHERE name = 'scsbank_bcp_back';   -- 0

USE scsbank_bcp_back;
SELECT COUNT(*) AS tables FROM sys.tables;                                        -- 17, all empty
A DACPAC carries schema, not encryption settings. Every database created this way starts unencrypted, which is why the next step comes before the data.

Enable TDE on the empty target

First see what already exists in master. Lab 5 may have created a master key and TDE_Cert on this instance:

USE master;
SELECT name FROM sys.symmetric_keys WHERE name = '##MS_DatabaseMasterKey##';
SELECT name, subject, expiry_date, thumbprint FROM sys.certificates WHERE name LIKE '%TDE%';

The key chain

Service Master Key ─▶ Database Master Key (master) ─▶ TDE certificate ─▶ Database Encryption Key (AES-256) ─▶ data pages

Choose one of the two options below. They differ only in where the certificate comes from.

Option A: SQL Server-generated certificate

You can reuse Lab 5's TDE_Cert, since one certificate can protect many databases. A certificate per database keeps custody and rotation simpler, so this creates a new one:

-- A1. master key (only if missing) + backup
USE master;
IF NOT EXISTS (SELECT 1 FROM sys.symmetric_keys WHERE name = '##MS_DatabaseMasterKey##')
BEGIN
    CREATE MASTER KEY ENCRYPTION BY PASSWORD = '<DMK_StrongPassword>';
    BACKUP MASTER KEY TO FILE = 'B:\Keys\master_DMK.key'
        ENCRYPTION BY PASSWORD = '<DMK_Backup_Password>';
END

-- A2. certificate + IMMEDIATE backup
CREATE CERTIFICATE TDE_Cert_Lab6
    WITH SUBJECT = 'TDE certificate for scsbank_bcp_back',
         EXPIRY_DATE = '2036-12-31';

BACKUP CERTIFICATE TDE_Cert_Lab6
    TO FILE = 'B:\Keys\TDE_Cert_Lab6.cer'
    WITH PRIVATE KEY (FILE = 'B:\Keys\TDE_Cert_Lab6.pvk',
                      ENCRYPTION BY PASSWORD = '<Cert_Backup_Password>');

-- A3. database encryption key + encryption on
USE scsbank_bcp_back;
CREATE DATABASE ENCRYPTION KEY WITH ALGORITHM = AES_256
    ENCRYPTION BY SERVER CERTIFICATE TDE_Cert_Lab6;     -- or TDE_Cert to reuse Lab 5's

USE master;
ALTER DATABASE scsbank_bcp_back SET ENCRYPTION ON;
Copy TDE_Cert_Lab6.cer, TDE_Cert_Lab6.pvk, master_DMK.key and their passwords off the server. Without them, backups of this database can't be restored anywhere else.

Option B: customer-provided certificate

Ask for the certificate with its private key (.pfx, or .cer + .pvk), its password through a separate channel, and its thumbprint. A public-only .cer can't be used for TDE.

mkdir B:\Keys\import -Force
icacls "B:\Keys\import" /inheritance:r /grant:r "Administrators:(OI)(CI)F" "SYSTEM:(OI)(CI)F" "NT Service\MSSQLSERVER:(OI)(CI)R"
# copy Customer_TDE.pfx into B:\Keys\import
USE master;
IF NOT EXISTS (SELECT 1 FROM sys.symmetric_keys WHERE name = '##MS_DatabaseMasterKey##')
    CREATE MASTER KEY ENCRYPTION BY PASSWORD = '<DMK_StrongPassword>';

CREATE CERTIFICATE Customer_TDE_Cert
    FROM FILE = 'B:\Keys\import\Customer_TDE.pfx'
    WITH FORMAT = 'PFX',
    PRIVATE KEY (DECRYPTION BY PASSWORD = '<pfx_password>');
-- .cer + .pvk instead:
--   FROM FILE = '...\Customer_TDE.cer'
--   WITH PRIVATE KEY (FILE = '...\Customer_TDE.pvk', DECRYPTION BY PASSWORD = '...')

-- Thumbprint must match the customer's; private key must be present
SELECT name, thumbprint, pvt_key_encryption_type_desc     -- ENCRYPTED_BY_MASTER_KEY, not NO_PRIVATE_KEY
FROM sys.certificates WHERE name = 'Customer_TDE_Cert';

USE scsbank_bcp_back;
CREATE DATABASE ENCRYPTION KEY WITH ALGORITHM = AES_256
    ENCRYPTION BY SERVER CERTIFICATE Customer_TDE_Cert;

USE master;
ALTER DATABASE scsbank_bcp_back SET ENCRYPTION ON;
Remove-Item B:\Keys\import\* -Force     # the customer keeps the master copy

SQL Server 2019 and earlier can't read .pfx directly. Convert it to .cer + .pvk with OpenSSL first. If the customer won't release the private key at all, use EKM with Azure Key Vault or an HSM instead.

Confirm before loading any data

SELECT DB_NAME(database_id) db, encryption_state_desc, percent_complete, encryptor_type
FROM sys.dm_database_encryption_keys WHERE database_id = DB_ID('scsbank_bcp_back');

Wait for ENCRYPTED. On an empty database that takes seconds. From here on, every page BCP writes is encrypted on disk.

Export data from Azure (bcp out)

Run in the same PowerShell window, so $pwd is still set:

$dir = "B:\Lab6\data"; $logs = "B:\Lab6\logs"
$tables = sqlcmd -S $az -d $azdb -U $user -P $pwd -l 120 -h -1 -W `
  -Q "SET NOCOUNT ON; SELECT s.name + '.' + t.name FROM sys.tables t JOIN sys.schemas s ON t.schema_id=s.schema_id WHERE t.is_ms_shipped=0 ORDER BY 1"

foreach ($t in $tables | Where-Object { $_ -and $_.Trim() -ne "" }) {
    $t = $t.Trim(); $log = "$logs\out_$t.log"
    for ($i = 1; $i -le 3; $i++) {
        bcp "$t" out "$dir\$t.dat" -S $az -d $azdb -U $user -P $pwd -N -l 120 -a 32768 -o $log
        if (Select-String -Path $log -Pattern "rows copied" -Quiet) { Write-Host "OK    $t"; break }
        Write-Host "RETRY $t ($i)"; Start-Sleep 30
    }
}
Select-String -Path "$logs\out_*.log" -Pattern "rows copied" | Measure-Object   # Count must be 17
FlagWhy
-d scsbank + two-part nameAzure doesn't accept db.schema.table
-U / -P, no -uSQL authentication; Azure's certificate is trusted, so keep validation on
-l 120 + retry loopSurvives a serverless wake-up
-a 32768Larger packets, faster over the internet
-NNative format: exact types, fastest

Then reopen Azure:

ALTER DATABASE scsbank SET READ_WRITE;     -- on cisql01

Import into the encrypted target (bcp in)

Get-ChildItem $dir -Filter *.dat | ForEach-Object {
    $t = $_.BaseName
    bcp "$t" in "$($_.FullName)" -S MSSQLSRV01 -d scsbank_bcp_back -T -u `
        -N -E -b 50000 -h "TABLOCK" -o "$logs\in_$t.log"
}
Select-String -Path "$logs\in_*.log" -Pattern "rows copied|Error" | Select Filename, Line
  • -E keeps identity values. Without it, the foreign-key links break.
  • -T -u: Windows authentication, trusting the local self-signed certificate. Drop -u once an organisation TLS certificate is installed.
  • Count the log lines: 17 tables need 17 rows copied. With -o, BCP prints nothing to the console, which is how failures hid in Lab 3.
  • TDE adds only a few percent of CPU to the load. Pages are encrypted as they're flushed to disk.

Re-trust constraints and validate

BCP skips foreign-key checks during the load, leaving constraints untrusted. Re-check them, which also tests data integrity:

USE scsbank_bcp_back;
DECLARE @sql NVARCHAR(MAX) = N'';
SELECT @sql += N'ALTER TABLE ' + QUOTENAME(s.name) + N'.' + QUOTENAME(t.name)
             + N' WITH CHECK CHECK CONSTRAINT ALL;' + CHAR(10)
FROM sys.tables t JOIN sys.schemas s ON t.schema_id = s.schema_id;
EXEC sp_executesql @sql;

SELECT COUNT(*) AS untrusted_fks FROM sys.foreign_keys WHERE is_not_trusted = 1;   -- 0
EXEC sp_updatestats;

Then run the baseline queries from the source section on scsbank_bcp_back. Row counts for all 17 tables, object counts and SUM(Balance) must equal Azure's.

  • A Msg 547 conflict means a parent table didn't load fully. Use the all-foreign-keys orphan query from Lab 3 to find it, then reload that table.
  • A child-only table that failed won't trigger any FK error. Only the row-count comparison catches it.

Verify TDE and the backup chain

SELECT name, is_encrypted FROM sys.databases WHERE name IN ('scsbank_bcp_back','tempdb');   -- both 1

SELECT DB_NAME(database_id) db, encryption_state_desc, key_algorithm, key_length, encryptor_type
FROM sys.dm_database_encryption_keys;

BACKUP DATABASE scsbank_bcp_back TO DISK = 'B:\Backup\scsbank_bcp_back_tde.bak'
    WITH COMPRESSION, CHECKSUM, INIT;
RESTORE VERIFYONLY FROM DISK = 'B:\Backup\scsbank_bcp_back_tde.bak' WITH CHECKSUM;

tempdb shows as encrypted automatically: SQL Server does this as soon as any database on the instance uses TDE.

Clean up the unencrypted copies

Remove-Item B:\Lab6\data\*.dat, B:\Lab6\scsbank_azure.dacpac -Force
  • Make sure cisql01/scsbank is back to READ_WRITE.
  • Disconnect tools from Azure so the free database can auto-pause.
  • Recreate application logins and users on the VM. They were excluded on purpose.
  • Schedule backups, DBCC CHECKDB and index maintenance as SQL Agent jobs. Azure did these for you.

Alternative: Azure Data Factory instead of BCP

For a repeatable or larger-scale copy, keep steps 1–5 (schema, TDE, freeze) and replace bcp with an ADF pipeline:

  1. Create a Data Factory and register a Self-hosted Integration Runtime on MSSQLSRV01.
  2. Create linked services for Azure SQL Database (cisql01) and SQL Server (MSSQLSRV01), both through the SHIR.
  3. Build the pipeline: Lookup the table list → ForEach → Copy from [schema].[table] to the same table, with table option None (the schema already exists) and identity insert on.
  4. Check every copy activity: rows read = rows written.

ADF copies straight from Azure to SQL Server with no .dat files on disk, so there's no unencrypted staging copy at all. The trade-off is a small per-run cost and more setup. Adding Change Tracking to the same pattern gives the low-downtime Lab 7.

  • Enable TDE before the data arrives whenever you control database creation. It's faster and leaves no unencrypted window.
  • The certificate choice is about ownership: generated when the DBA team owns the keys, imported when the customer or security team must keep custody.
  • The data files between export and load are the weak point. Lock the folder down, delete the files promptly, or use ADF to skip them entirely.
  • Validate with logs, constraint re-checks and row counts. Each one catches failures the others miss.
