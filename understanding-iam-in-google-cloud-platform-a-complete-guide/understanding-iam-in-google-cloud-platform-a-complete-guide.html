Understanding IAM in Google Cloud Platform: A Complete Guide

By Sunke Nithin · August 9, 2025   CloudGCP

In cloud computing, controlling who can access what is foundational to security and governance. Google Cloud IAM (Identity and Access Management) provides a flexible, powerful system for managing access to your cloud resources. Whether you're running a small proof of concept or managing enterprise workloads, understanding IAM is essential to operating securely in GCP.

1What is IAM in GCP?

IAM in Google Cloud is a framework that defines:

Whothe identity (principal)
can do whatthe role and its permissions

IAM controls access across all GCP services, such as Compute Engine, Cloud Storage, BigQuery, Cloud Functions and more.

2Core Components of IAM

1. Identities (who is accessing?)

Identities — also called principals — are the entities that interact with GCP.

allUsers and allAuthenticatedUsers make a resource public. Grant them only when that's truly intended (for example a public website bucket).

2. Resources (what is being accessed?)

Resources are GCP services and components such as:

  • Projects
  • Virtual machines (Compute Engine)
  • Cloud Storage buckets
  • BigQuery datasets
  • Pub/Sub topics
  • APIs

3. Roles (what access is granted?)

A role is a collection of permissions. There are three kinds:

🔹 Predefined roles

Google provides fine-grained, service-specific roles, for example:

  • roles/storage.objectViewer — read-only access to Cloud Storage objects
  • roles/compute.admin — full control of Compute Engine resources
  • roles/bigquery.dataViewer — read BigQuery data and metadata

🔹 Custom roles

You can create custom roles containing only the permissions your team needs.

⚠️ Basic roles (not recommended for production)

  • roles/owner — full access, including managing IAM and billing (dangerous!)
  • roles/editor — create, change and delete most resources, but not manage IAM
  • roles/viewer — read-only access to most resources
Use predefined or custom roles instead of basic roles to follow the principle of least privilege. Basic roles cover almost every service in the project, so they grant far more than most people need.

4. Policy

An IAM allow policy is a collection of bindings; each binding attaches a list of members (principals) to a role.

JSON
{
  "bindings": [
    {
      "role": "roles/storage.admin",
      "members": [
        "user:alice@example.com",
        "group:devops@example.com"
      ]
    }
  ]
}

3IAM Policy Hierarchy

IAM policies are hierarchical and can be set at each of these levels:

  • Policies are inherited downwards. A resource's effective access is the union of its own policy and every policy above it.
  • This lets you set broad access at the organization or folder level and add more specific grants lower down.
Allow policies are additive: a lower level can add access but can't take away access granted higher up. To block access that's inherited, use an IAM deny policy — or, better, grant it lower in the hierarchy in the first place.

4How to Manage IAM

Google Cloud Console

  1. Go to IAM & Admin → IAM.
  2. Click Grant access.
  3. Enter the principal (user, group or service account).
  4. Assign a role.
  5. Click Save.

gcloud CLI

GCLOUD
gcloud projects add-iam-policy-binding PROJECT_ID \
  --member="user:john@example.com" \
  --role="roles/compute.viewer"

Terraform

TERRAFORM
resource "google_project_iam_member" "viewer" {
  project = "my-project-id"
  role    = "roles/viewer"
  member  = "user:john@example.com"
}
Which Terraform resource? google_project_iam_member adds one member and leaves everyone else alone. google_project_iam_binding is authoritative for its role — it removes anyone holding that role who isn't in its members list — so use it only when Terraform should own the full membership of that role.

IAM in action: a scenario

Goal: give a developer read-only access to the BigQuery datasets in a project, with the ability to run queries.

  1. Go to IAM & Admin → IAM and click Grant access.
  2. Add the principal dev@example.com.
  3. Assign roles/bigquery.dataViewer (read tables) and roles/bigquery.jobUser (run query jobs).
GCLOUD
gcloud projects add-iam-policy-binding PROJECT_ID \
  --member="user:dev@example.com" --role="roles/bigquery.dataViewer"
gcloud projects add-iam-policy-binding PROJECT_ID \
  --member="user:dev@example.com" --role="roles/bigquery.jobUser"

The developer can now read and query the data, but can't modify or delete the datasets. dataViewer on its own would let them see the data but not run queries.

6IAM Best Practices

PracticeWhy it matters
Use least privilegeMinimizes the damage if credentials are compromised
Prefer groups over individualsMuch easier to manage at scale
Audit IAM policies regularlyCatches overly broad permissions
Use custom roles for sensitive workflowsFine-grained control
Avoid the Owner roleToo much power, especially in production
Use service accounts for automationSecure and traceable — and avoid downloading their keys where you can

Final Thoughts

IAM is a cornerstone of security and compliance in Google Cloud. Mastering it helps you prevent data breaches, enforce the principle of least privilege, simplify user and service-account access, and audit and monitor access effectively. Whether you're building in the free tier or scaling to enterprise workloads, understanding IAM is critical to a secure, manageable cloud foundation.
