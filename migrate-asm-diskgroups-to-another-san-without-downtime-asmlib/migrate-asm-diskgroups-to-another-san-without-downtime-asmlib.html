Migrating ASM Disk Groups to New Storage Without Downtime (ASMLIB)

By Sunke Nithin · June 26, 2019   DatabaseOracleStorage

ASM can move a disk group from an old SAN or disk array to a new one while databases stay open: add the new disks, let ASM rebalance the data onto them, then drop the old disks. Here the DATA disk group moves from ten old LUNs to ten new ones, all labelled with ASMLIB. The same works for disk groups holding OCR, voting files and the ASM spfile.

Before You Start

  • Take and validate a backup of every database in the disk group.
  • Present the new LUNs to all cluster nodes, with multipathing configured (see LUN migration).
  • The new disks should be the same size and performance as the old ones — ASM balances data by capacity, and mixed sizes cause uneven I/O.
  • The new disk group capacity must hold all current data.

1Label the New Disks with ASMLIB

BASH
# as root, on one node: label the new LUNs (partitions on the multipath devices)
oracleasm createdisk ASMDISK_NEW_SAN_1 /dev/mapper/mpathbp1
oracleasm createdisk ASMDISK_NEW_SAN_2 /dev/mapper/mpathcp1
# ... one per new LUN, up to ASMDISK_NEW_SAN_10
BASH
# as root, on every other RAC node
oracleasm scandisks
oracleasm listdisks          # old AND new disks must be listed on every node
BASH
/usr/sbin/oracleasm-discover 'ORCL:*'
Discovered disk: ORCL:ASMDISK_NEW_SAN_1 [40017852 blocks (20489140224 bytes), maxio 512]
...
Discovered disk: ORCL:ASMDISK_OLD_SAN_10 [40017852 blocks (20489140224 bytes), maxio 512]

2Check ASM Can See Them

SQL
-- on every ASM instance (+ASM1, +ASM2 ...)
show parameter asm_diskstring
-- asm_diskstring   string   ORCL:*
SQL
set lines 200
col path for a30
select path, header_status, os_mb from v$asm_disk order by path;
-- new disks: HEADER_STATUS = PROVISIONED (ASMLIB-labelled, not yet in a disk group)
-- old disks: MEMBER

Before adding disks, Oracle recommends validating them as described in My Oracle Support Doc ID 557348.1 (adding disks to an existing disk group) — for example checking every node sees the same disks and that they are writable by the grid user.

3Swap the Disks in One Operation

SQL
-- one statement: add the new disks and drop the old ones -> a single rebalance
alter diskgroup DATA
  add disk 'ORCL:ASMDISK_NEW_SAN_1', 'ORCL:ASMDISK_NEW_SAN_2', 'ORCL:ASMDISK_NEW_SAN_3',
           'ORCL:ASMDISK_NEW_SAN_4', 'ORCL:ASMDISK_NEW_SAN_5', 'ORCL:ASMDISK_NEW_SAN_6',
           'ORCL:ASMDISK_NEW_SAN_7', 'ORCL:ASMDISK_NEW_SAN_8', 'ORCL:ASMDISK_NEW_SAN_9',
           'ORCL:ASMDISK_NEW_SAN_10'
  drop disk ASMDISK_OLD_SAN_1, ASMDISK_OLD_SAN_2, ASMDISK_OLD_SAN_3, ASMDISK_OLD_SAN_4,
            ASMDISK_OLD_SAN_5, ASMDISK_OLD_SAN_6, ASMDISK_OLD_SAN_7, ASMDISK_OLD_SAN_8,
            ASMDISK_OLD_SAN_9, ASMDISK_OLD_SAN_10
  rebalance power 11;

Doing the add and drop in one statement triggers a single rebalance, so each extent moves once. With two separate statements, data is first spread over old + new disks and then moved again off the old ones:

SQL
alter diskgroup DATA add disk 'ORCL:ASMDISK_NEW_SAN_1', ... rebalance power 11;
-- wait for the rebalance to finish, then
alter diskgroup DATA drop disk ASMDISK_OLD_SAN_1, ... rebalance power 11;

Higher rebalance power finishes sooner but uses more I/O; lower it during business hours (alter diskgroup DATA rebalance power 4;).

4Wait for the Rebalance

SQL
select group_number, operation, state, power, sofar, est_work, est_minutes
from   gv$asm_operation;
-- no rows selected  = rebalance finished

select name, path, header_status, mount_status from v$asm_disk order by path;
-- old disks now show HEADER_STATUS = FORMER

The old disks stay in the disk group (status DROPPING) until the rebalance finishes. When it does, they show FORMER and the migration is complete.

BASH
# if the disk group holds OCR / voting files, confirm afterwards (as root)
ocrcheck
crsctl query css votedisk
# ASM spfile location
asmcmd spget

5Clean Up the Old Disks

BASH
# only after the old disks show FORMER on every node
oracleasm deletedisk ASMDISK_OLD_SAN_1      # on one node
oracleasm scandisks                         # on the others

Only then ask the storage team to unmap the old LUNs, and remove their multipath entries.

Rules

  • Never run oracleasm createdisk or deletedisk on a disk that is still a member of a disk group.
  • Never remove, reformat or resize an old LUN until its ASM disk has been fully dropped (status FORMER).
  • On 10g a stalled drop isn't restarted automatically; restart it with alter diskgroup DATA rebalance power 11;. Since 11g ASM resumes rebalances by itself.
