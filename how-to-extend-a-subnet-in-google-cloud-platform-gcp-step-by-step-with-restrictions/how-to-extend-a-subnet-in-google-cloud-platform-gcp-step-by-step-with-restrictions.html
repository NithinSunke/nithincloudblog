How to Extend a Subnet in Google CLOUD Platform (GCP): Step by Step, with Restrictions

By Sunke Nithin · August 9, 2025   CLOUDGCP

When a subnet runs out of addresses, GCP lets you expand its primary range in place — no downtime, no change to existing VMs. But the expansion is one-way and has rules. Here I grow subnet-us-central1-ext from 10.0.0.0/24 (256 addresses) to 10.0.0.0/23 (512).

Restrictions

RuleDetails
Grow onlyYou can only make the prefix shorter (/24 → /23). A subnet can never shrink, so expand in modest steps.
Same starting addressThe new range keeps the base address and must contain the old one. 10.0.1.0/24 can't become 10.0.1.0/23 — that isn't a valid /23; it would be 10.0.0.0/23.
No overlapThe larger range must not overlap any other subnet in the VPC, or in peered VPCs, or routes that conflict.
Primary range onlySecondary ranges (alias IPs, GKE pods/services) can't be expanded; add a new secondary range instead.
Auto-mode limitSubnets of an auto-mode VPC can only grow to /16 within 10.128.0.0/9; to go further, convert the VPC to custom mode.

Permissions: roles/compute.networkAdmin or equivalent.

Method 1: Cloud Console

  1. VPC network → VPC networks → your VPC (gcplab-vpc) → Subnets → the subnet.
  2. Click Edit.
  1. Change Primary IPv4 range to 10.0.0.0/23 and click Save.

The console checks the new range against the rules above; if it's valid the change is applied within seconds.

Method 2: gcloud CLI

gcloud takes only the new prefix length — the base address can't change, so there's nothing else to specify:

BASH
gcloud compute networks subnets expand-ip-range subnet-us-central1-ext \
    --region=us-central1 \
    --prefix-length=23

gcloud asks for confirmation, because the change can't be undone.

Verify

BASH
gcloud compute networks subnets describe subnet-us-central1-ext \
    --region=us-central1 --format="value(ipCidrRange)"
10.0.0.0/23

Tips

  • Check address usage first (IP addresses page, or Network Intelligence's IP utilization) — expand when you need to, not just in case.
  • Firewall rules and routes that list the old CIDR explicitly need updating.
  • If you can't expand (overlap, secondary range), add a new subnet in the same region instead.
