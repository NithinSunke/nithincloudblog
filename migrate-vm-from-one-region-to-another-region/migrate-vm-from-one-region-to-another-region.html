Migrate an OCI Compute VM from One Region to Another

By Sunke Nithin · January 9, 2025   LinuxOCIMigrationCLOUD

OCI has no "move instance to another region" button, but the building blocks are there. The boot volume travels as a custom image through Object Storage; block volumes travel as backups copied to the other region. Here I move the VM zdm from Saudi Arabia West (Jeddah) to Saudi Arabia Central (Riyadh), including its 100 GB data volume.

Custom image → Object Storage → other region → custom image → new VM

Part 1 — The Boot Volume

1Create a Custom Image

On the instance page, More actions → Create custom image. The instance is taken offline while the image is created, so shut the applications (and ideally the OS) down cleanly first:

A custom image contains only the boot volume; attached block volumes are handled separately in Part 2.

2Set Up Bucket Replication to the Target Region

In the source region, open the bucket that will receive the export (migbkt) and create a Replication Policy to a bucket in the target region (mybucket in Riyadh). Anything written to the source bucket is copied across automatically:

Replication needs an IAM policy allowing the Object Storage service in the source region to manage objects in your compartment (e.g. Allow service objectstorage-me-jeddah-1 to manage object-family in compartment sn_compute). Alternatively, skip replication and export to a pre-authenticated request URL, then import from that URL in the target region.

3Export the Image

On the custom image, click Export, choose the bucket and the OCI format (QCOW2 plus OCI metadata, so launch options are preserved):

Once the export finishes the object appears in the source bucket, and shortly after in the replicated bucket in Riyadh.

4Import the Image in the Target Region

Switch to the target region: Compute → Custom images → Import image, from the Object Storage bucket, image type OCI:

5Create the Instance in the Target Region

Compute → Instances → Create instance. Under Image and shape, Change image → My images and select the imported image; choose a shape:

I placed it in a private subnet of the Riyadh VCN, added my SSH public key and kept the default boot volume:

6Connect and Check

With no public IP, I connected through an OCI Bastion session. The new instance has exactly the same boot volume contents — software, users and configuration — as the source:

Part 2 — Block Volumes

7Back Up the Block Volume

From the source instance, Attached block volumes → the volume → Block Volume Backups → Create Block Volume Backup (full). For a consistent copy, stop the applications or unmount the file system first:

8Copy the Backup to the Target Region

On the backup, Copy to Another Region, then watch it appear in the target region's backup list:

9Restore a Block Volume in the Target Region

In the target region, on the copied backup: Restore Block Volume. Put it in the same availability domain as the new instance:

10Attach It to the New Instance

On the new instance, Attached block volumes → Attach block volume. Use the same device path as on the source (/dev/oracleoci/oraclevdb) so the existing /etc/fstab entry still matches:

11Verify

The LVM volume group on the restored disk is found and /u01 is mounted, just like on the source:

Make sure block-volume entries in /etc/fstab use _netdev,nofail. Without nofail, an instance created from the image before the volume is attached can hang at boot waiting for /u01.
FSTAB
# /etc/fstab on the source — consistent device path + _netdev,nofail
/dev/mapper/zdm_vg-zdm_lv  /u01  xfs  defaults,_netdev,nofail  0 2

Alternatives

  • Boot volume backup copy: back up the boot volume, copy the backup to the other region, restore it and launch an instance from the boot volume — no custom image or bucket needed.
  • Volume group backups copy the boot volume and all block volumes together, consistently.
  • For ongoing protection rather than a one-off move, use Full Stack Disaster Recovery or cross-region volume replication.

After the move, update DNS and application configuration with the new IPs, and terminate the source instance and its volumes once you're done.
