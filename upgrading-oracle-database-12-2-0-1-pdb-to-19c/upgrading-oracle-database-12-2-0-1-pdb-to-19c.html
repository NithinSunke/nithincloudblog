Upgrading an Oracle Database 12.2.0.1 PDB to 19c

By Sunke Nithin · May 21, 2024   DatabaseOracleUpgradeMigration

This post shows how to move a pluggable database (PDB) from a 12.2.0.1 container database to a 19c container database on another server, and upgrade it there. A refreshable PDB clone copies the data ahead of time, so the downtime window only covers the final refresh and the upgrade itself.

Assumptions

  • The source and target VMs are already built and ready for the upgrade.
  • The source database is 12.2.0.1 and the target database is 19c (both multitenant).
  • An NFS share is mounted on both servers (here /nfsshare/oracle/backup) for copying files.

1Check Plug-in Compatibility of the PDB

Start by checking whether the PDB can be plugged into the new-release CDB.

SourceGenerate the PDB description XML

SQL
EXEC DBMS_PDB.DESCRIBE('/home/oracle/O122V.xml', 'O122V');
Show output

NFS shareCopy the XML file to the share

BASH
cd /nfsshare/oracle/backup
cp ~/O122V.xml .
Show output

TargetCheck compatibility on the 19c CDB

SQL
SET SERVEROUTPUT ON
BEGIN
  IF DBMS_PDB.CHECK_PLUG_COMPATIBILITY('/nfsshare/oracle/backup/O122V.xml', 'O122V') THEN
    DBMS_OUTPUT.PUT_LINE('SUCCESS');
  ELSE
    DBMS_OUTPUT.PUT_LINE('ERROR');
  END IF;
END;
/
Show output
A result of ERROR isn't automatically a blocker — moving a PDB to a higher release is expected to raise a "PDB needs upgrade" type of message. Review the details with: SELECT type, message, status FROM pdb_plug_in_violations WHERE name = 'O122V'; and fix any other errors before continuing.

2Create a Refreshable PDB on the Target

While waiting for downtime to start, create a refreshable PDB on the target. Copying the PDB ahead of time avoids doing a full copy during downtime: when it's refreshed later, only the most recent changes from the source are applied, which is much faster than a full clone.

SourceCreate a common user for the database link

SQL
CREATE USER c##clone_user IDENTIFIED BY <password> CONTAINER=ALL;
GRANT CREATE SESSION, CREATE PLUGGABLE DATABASE TO c##clone_user CONTAINER=ALL;
Show output

TargetCreate a database link to the source CDB

SQL
CREATE DATABASE LINK clone_link
  CONNECT TO c##clone_user IDENTIFIED BY <password>
  USING 'ol7122v01.scslabs.com/o122v';
Show output

TargetCheck that the link works

SQL
SELECT * FROM dual@clone_link;
SELECT count(*) FROM all_objects@clone_link;
Show output

TargetCreate the refreshable PDB

Create it with REFRESH MODE MANUAL, so it's only refreshed when you ask:

SQL
CREATE PLUGGABLE DATABASE O122V FROM O122V@clone_link
  PARALLEL 4
  REFRESH MODE MANUAL;
Show output

TargetRefresh periodically

Refresh the PDB now and then to keep the final refresh short:

SQL
ALTER PLUGGABLE DATABASE O122V REFRESH;
Show output

SourceCreate a test table

To prove that changes made after the clone reach the target, create a small test table in the source PDB:

SQL
ALTER SESSION SET CONTAINER=O122V;
CREATE TABLE tst1 (sno NUMBER, status VARCHAR2(10));
INSERT INTO tst1 VALUES (1, 'success');
COMMIT;
Show output
In the original run this table was created in the SYS schema. That's fine for a quick lab test, but in a real environment use an application schema — don't create your own objects in SYS.

3Final Refresh and Convert (Downtime Starts)

SourceClose the source PDB

SQL
ALTER PLUGGABLE DATABASE O122V CLOSE IMMEDIATE;
SHOW PDBS
Show output

TargetDo the final refresh

SQL
SHOW PDBS
ALTER PLUGGABLE DATABASE O122V REFRESH;
Show output

TargetConvert the refreshable PDB into a regular PDB

SQL
ALTER PLUGGABLE DATABASE O122V REFRESH MODE NONE;
Show output
After REFRESH MODE NONE, the PDB can no longer be refreshed from the source. Keep the source PDB closed but intact until the upgrade is validated — it's your fallback.

4Upgrade the PDB

TargetOpen the PDB in upgrade mode

SQL
ALTER PLUGGABLE DATABASE O122V OPEN UPGRADE;
SHOW PDBS
Show output

The PDB shows open mode MIGRATE and RESTRICTED = YES.

TargetRun dbupgrade against the PDB

BASH
dbupgrade -c O122V -l /nfsshare/oracle/backup/upgrade -N 4
OptionMeaning
-c O122VUpgrade only this PDB (inclusion list).
-l <dir>Directory for the upgrade log files.
-N 4Number of SQL processes to use for the PDB.
Show start of the run
Show end of the run

In this lab the upgrade took about 43 minutes. The summary report is written to upg_summary.log in the log directory — check it for errors.

5Open the PDB and Validate the Data

SQL
ALTER PLUGGABLE DATABASE O122V OPEN;
SHOW PDBS
ALTER SESSION SET CONTAINER=O122V;
SELECT * FROM tst1;
Show output

The PDB opens READ WRITE and unrestricted, and the test row inserted on the source just before downtime is there — the final refresh carried it across.

Post-upgrade checks worth running: recompile invalid objects with @?/rdbms/admin/utlrp.sql inside the PDB, confirm no open issues in pdb_plug_in_violations, apply the 19c release update with datapatch if the target home is patched, and save the open state with ALTER PLUGGABLE DATABASE O122V SAVE STATE; so it opens automatically after a restart.
