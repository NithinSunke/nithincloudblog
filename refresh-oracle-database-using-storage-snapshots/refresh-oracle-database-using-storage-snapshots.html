Refresh an Oracle Database Using Storage Snapshots

By Sunke Nithin · May 20, 2024   DatabaseOracleMigration

Cloning a big database with RMAN takes hours; a storage snapshot takes seconds. In this post I refresh a clone database by snapshotting the disks of a running source database, attaching the copies to a new server, and recovering. I don't have a SAN in my lab, so VirtualBox disk snapshots and clonehd stand in for the storage array — every database step is the same.

begin backup→snapshot→clone disks→end backup→mount clone→recover→open

Assumptions

  • A new VM (the clone server) is built, with the Oracle prerequisites installed.
  • The source keeps the Oracle home and the database files (data files, control files, online redo logs) on dedicated disks/LUNs, so they can be cloned and attached to the new server.
  • The source database is in ARCHIVELOG mode.

1Put the Source Database in Backup Mode

SQL · SOURCE
alter database begin backup;

In backup mode Oracle writes whole blocks to redo the first time they change, so a copy taken mid-write can still be recovered.

2Take the Snapshot

On a storage array, this is the LUN snapshot (take all the database's LUNs together in one consistency group). In VirtualBox, snapshot the running VM:

POWERSHELL
VBoxManage snapshot ol7_19_vagrant take ol7_19_vagrant_snap1 --live

3End Backup Mode

As soon as the snapshot is taken, take the source out of backup mode — it generates extra redo while it's in it:

SQL · SOURCE
alter database end backup;

4Clone the Disks

The snapshot froze the base disks, so they can now be copied safely — the Oracle home disk (u01) and the data disk (u02):

POWERSHELL
VBoxManage clonehd D:\VMBOXES\ol7_19_vagrant\ol7_19_u01.vdi D:\VMBOXES\ol7_19c_vagrant\ol7_19_u01.vdi --format VDI
VBoxManage clonehd D:\VMBOXES\ol7_19_vagrant\ol7_19_u02.vdi D:\VMBOXES\ol7_19c_vagrant\ol7_19_u02.vdi --format VDI

Attach the cloned disks to the new VM and mount them on the same paths as on the source.

5Mount the Clone Database

BASH · CLONE
. scripts/setEnv.sh
sqlplus / as sysdba
SQL · CLONE
startup mount

6Recover and Open

SQL · CLONE
recover database;
alter database open;
show pdbs

Recovery applies the redo from the cloned online logs, and the clone opens with its PDB.

Because the control file and online redo logs were cloned with the data files, a plain recover database finds all the redo it needs. If the redo logs live on a disk you didn't clone, copy the archived logs generated during backup mode to the clone and recover with recover database until cancel using backup controlfile, then alter database open resetlogs.

7Drop the Snapshot

POWERSHELL
VBoxManage snapshot ol7_19_vagrant delete ol7_19_vagrant_snap1

After the Refresh

The clone is an exact copy — same database name and DBID as the source. Before using it alongside the source:
  • Change the DBID and name with nid (DBNEWID) so RMAN catalogs and monitoring tools don't confuse the two.
  • Point database links, scheduler jobs and application connections away from production.
  • Update listener and tnsnames.ora entries for the new host.
Skipping backup mode: from 12c, if the storage takes a crash-consistent snapshot of all database files at once, backup mode isn't required — recover the clone with RECOVER DATABASE … SNAPSHOT TIME '<time>'. Backup mode is still the simplest choice when the snapshots aren't atomic across all LUNs.
