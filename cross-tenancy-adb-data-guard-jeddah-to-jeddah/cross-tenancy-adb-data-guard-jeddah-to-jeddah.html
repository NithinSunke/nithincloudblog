Cross-Tenancy Autonomous Data Guard in One Region: Source and Target in Jeddah with the OCI CLI

By Sunke Nithin · October 17, 2026   CLOUDOCIADBData Guard

Autonomous Data Guard can keep a standby in a different OCI tenancy. Here the source database CTRATP lives in A_tenancy and its standby is created in B_tenancy — both in the same region, Jeddah (me-jeddah-1). The Console can't set up a cross-tenancy standby, so everything is done with the OCI CLI from Windows PowerShell.

Source and Target

Source (primary)Target (standby)
TenancyA_tenancyB_tenancy
Regionme-jeddah-1me-jeddah-1
DatabaseCTRATP — 2 ECPU, 20 GB, Transaction Processingcreated by this procedure
Compartmentnslabs (nested)Operations (top level)
Tenancy home region (IAM writes)eu-frankfurt-1ap-mumbai-1
CLI profile — Data Guard work (Jeddah)A_tenancyB_tenancy
CLI profile — IAM writes (home region)A_tenancy_frankfurtB_tenancy_mumbai

Both databases are in Jeddah; the other two regions only matter for identity. IAM writes always go to a tenancy's home region — Frankfurt for A, Mumbai for B — while every database call goes to Jeddah. So each tenancy gets two profiles: one for its home region and one for Jeddah. The CLI picks its endpoint from the profile's region= (or --region), never from the region inside an OCID.

What this protects against

RiskCovered?
Loss of a tenancy, accidental deletion, compartment or account compromiseYes
Database or instance failureYes
A Jeddah regional outageNo — both copies are in Jeddah
Why not another region? I first tried to put the target in Mumbai (B_tenancy's home region). Autonomous Data Guard refused it with a 404, because a cross-region standby must be in one of the source region's paired DR regions, and Mumbai isn't paired with Jeddah. The identical command against Jeddah worked straight away. To see which regions are allowed, open the source database → Disaster recovery → Add peer database and look at the region list.

Prerequisites

  • OCI CLI installed, with an API key uploaded for your user in both tenancies.
  • B_tenancy subscribed to me-jeddah-1 (region menu → Manage Regions → Subscribe). Subscribing is permanent, needs tenancy-admin rights, and takes a while — start it first.
  • The source isn't Free Tier and doesn't use a customer-managed (Vault) key — not supported with a cross-tenancy standby.
  • Tenancy-admin rights in both tenancies to create the policies.

1CLI Profiles

C:\Users\<user>\.oci\config:

OCI CONFIG
[A_tenancy]
user=ocid1.user.oc1..<A-user-ocid>
fingerprint=<key-fingerprint>
tenancy=ocid1.tenancy.oc1..<A-tenancy-ocid>
region=me-jeddah-1
key_file=C:/Users/<user>/.oci/oci_api_key.pem

[A_tenancy_frankfurt]
# same user, tenancy and key as A_tenancy - A's home region, for IAM writes
user=ocid1.user.oc1..<A-user-ocid>
fingerprint=<key-fingerprint>
tenancy=ocid1.tenancy.oc1..<A-tenancy-ocid>
region=eu-frankfurt-1
key_file=C:/Users/<user>/.oci/oci_api_key.pem

[B_tenancy]
# B's Data Guard region - where the standby is created and managed
user=ocid1.user.oc1..<B-user-ocid>
fingerprint=<key-fingerprint>
tenancy=ocid1.tenancy.oc1..<B-tenancy-ocid>
region=me-jeddah-1
key_file=C:/Users/<user>/.oci/oci_api_key.pem

[B_tenancy_mumbai]
# same user, tenancy and key as B_tenancy - B's home region, for IAM writes
user=ocid1.user.oc1..<B-user-ocid>
fingerprint=<key-fingerprint>
tenancy=ocid1.tenancy.oc1..<B-tenancy-ocid>
region=ap-mumbai-1
key_file=C:/Users/<user>/.oci/oci_api_key.pem

Prove authentication before anything else — this call needs valid credentials and almost no permissions:

POWERSHELL
oci os ns get --profile A_tenancy
oci os ns get --profile B_tenancy_mumbai
oci os ns get --profile B_tenancy          # Jeddah: 401 = B not subscribed to Jeddah yet
POWERSHELL
oci iam region-subscription list --profile B_tenancy_mumbai --output table
# me-jeddah-1 must show READY

If the same API key is uploaded in both tenancies (as here), remember to replace it in both when you rotate it.

2Variables and Source Details

POWERSHELL
# Tenancy A, the primary
$env:SRC_TENANCY_OCID     = '<A-tenancy-ocid>'
$env:SRC_PRIMARY_CMP_OCID = '<primary-compartment-ocid>'
$env:PRIMARY_ADB_OCID = oci db autonomous-database list `
  --profile A_tenancy `
  --compartment-id $env:SRC_PRIMARY_CMP_OCID `
  --display-name 'CTRATP' `
  --query 'data[0].id' --raw-output

# Tenancy B, the standby side
$env:TGT_TENANCY_OCID     = '<B-tenancy-ocid>'
$env:TGT_STANDBY_CMP_OCID = '<operations-compartment-ocid>'

# echo every variable - PowerShell returns "" for a misspelt name
$env:PRIMARY_ADB_OCID
$env:TGT_STANDBY_CMP_OCID

Echo every variable — PowerShell silently returns an empty string for a misspelt name. Then record the source's shape; the target inherits it:

POWERSHELL
oci db autonomous-database get --profile A_tenancy `
  --autonomous-database-id $env:PRIMARY_ADB_OCID `
  --query 'data.{name:"display-name", dbName:"db-name", state:"lifecycle-state",
           workload:"db-workload", ecpu:"compute-count", storage:"data-storage-size-in-gbs",
           license:"license-model", key:"key-store-id", free:"is-free-tier"}'

3IAM in the Target Tenancy (B_tenancy)

B_tenancy owns the group that does the work. It needs permission to create the standby in its own compartment, and an Endorse saying what the group may do in A_tenancy. IAM writes go to B's home region, Mumbai, so use the B_tenancy_mumbai profile:

POWERSHELL
$env:DEST_GROUP_OCID = oci iam group create `
  --profile B_tenancy_mumbai `
  --compartment-id $env:TGT_TENANCY_OCID `
  --name ADG-CrossTenancy-Admins `
  --description "Creates and manages the cross-tenancy ADG standby" `
  --query 'data.id' --raw-output

oci iam user-group-membership add --profile B_tenancy_mumbai `
  --user-id <B-user-ocid> `
  --group-id $env:DEST_GROUP_OCID

Policy cross-tenancy-adb-adg in B's root compartment:

POLICY
Define tenancy SourceTenancy as <A-tenancy-ocid>
Allow group ADG-CrossTenancy-Admins to manage autonomous-database-family in compartment Operations
Endorse group ADG-CrossTenancy-Admins to manage autonomous-database-family in tenancy SourceTenancy

4IAM in the Source Tenancy (A_tenancy)

A_tenancy Admits B's group to the source database. This write goes to Frankfurt, A's home region:

POLICY
Define tenancy DestinationTenancy as <B-tenancy-ocid>
Define group DestGroup as <ADG-CrossTenancy-Admins-group-ocid>
Admit group DestGroup of tenancy DestinationTenancy to manage autonomous-database-family in compartment id <primary-compartment-ocid>
POWERSHELL
$aPolicy = @(
  "Define tenancy DestinationTenancy as $env:TGT_TENANCY_OCID",
  "Define group DestGroup as $env:DEST_GROUP_OCID",
  "Admit group DestGroup of tenancy DestinationTenancy to manage autonomous-database-family in compartment id $env:SRC_PRIMARY_CMP_OCID"
)
$aPolicy | ConvertTo-Json | Set-Content -Encoding ascii a-policy.json

oci iam policy create --profile A_tenancy_frankfurt `
  --compartment-id $env:SRC_TENANCY_OCID `
  --name cross-tenancy-adb-adg-admit `
  --description "Admit B_tenancy's ADG group to the Jeddah primary" `
  --statements file://a-policy.json

# later updates need --statements and --version-date together
oci iam policy update --profile A_tenancy_frankfurt `
  --policy-id <admit-policy-ocid> `
  --statements file://a-policy.json `
  --version-date "" --force
Endorse and Admit. Endorse lives in the tenancy that owns the group; Admit in the tenancy that owns the resource. Neither works alone — the effective permission is the intersection, so keep the verb and resource type identical on both sides. These statements are only valid in the root compartment; the group must contain your user; use compartment id <ocid> for the nested source compartment. The screenshots show an earlier read autonomous-databases revision — I use manage autonomous-database-family on both sides.

Wait about ten minutes after each policy change before testing; quicker retries see the old state.

5Prove the Cross-Tenancy Access

Read the source database as B's group, in Jeddah:

POWERSHELL
oci db autonomous-database get --profile B_tenancy `
  --autonomous-database-id $env:PRIMARY_ADB_OCID `
  --query 'data.{name:"display-name", state:"lifecycle-state", role:role}'

{
  "name": "CTRATP",
  "role": null,
  "state": "AVAILABLE"
}

The B_tenancy profile already points at Jeddah, so no --region is needed. Success means IAM is right (role: null just means no peer yet). A 404 here is either a call sent to the wrong region or a policy gap; a 401 means B's credentials don't work in Jeddah yet (subscription or replication) — policies aren't even consulted.

6Create the Standby in Jeddah

POWERSHELL
oci db autonomous-database create-cross-tenancy-disaster-recovery-details `
  --profile B_tenancy `
  --compartment-id $env:TGT_STANDBY_CMP_OCID `
  --source-id $env:PRIMARY_ADB_OCID `
  --disaster-recovery-type ADG `
  --display-name "CTRATP-StandbyXTenancy-JED"

Only --compartment-id, --source-id and --disaster-recovery-type are required — no password, wallet, character set or sizing; the standby takes those from the source.

Provisioning took just under five minutes. The API reports disaster-recovery-region-type: REMOTE and dataguard-region-type: REMOTE_STANDBY_DG_REGION — "remote" here means the other tenancy, not another region.

7Verify

The target's Disaster recovery tab shows Local peer: 1 — the same-region standby — and the peer row: CTRATP (cross-tenancy), role Primary, Available, Saudi Arabia West (Jeddah). (My screenshots still show the first display name, CTRATP-StandbyMumbai; I renamed it afterwards.) From the CLI:

POWERSHELL
# target (standby), B_tenancy
oci db autonomous-database get --profile B_tenancy `
  --autonomous-database-id <standby-ocid> `
  --query 'data.{role:role, state:"lifecycle-state", dg:"is-data-guard-enabled", peers:"peer-db-ids"}'

# source (primary), A_tenancy
oci db autonomous-database get --profile A_tenancy `
  --autonomous-database-id $env:PRIMARY_ADB_OCID `
  --query 'data.{role:role, peers:"peer-db-ids", dg:"is-data-guard-enabled"}'

Each side lists the other in peer-db-ids; is-data-guard-enabled turns true when provisioning finishes. The Full Stack DR warning about missing permissions is harmless unless you use Full Stack DR.

8Switchover

A switchover swaps the roles with no data loss — use it for drills; fail over only when the source is really lost. Both peers are in Jeddah, so the same-region form applies:

POWERSHELL
oci db autonomous-database switchover --profile B_tenancy `
  --autonomous-database-id <standby-ocid> `
  --peer-db-id $env:PRIMARY_ADB_OCID `
  --wait-for-state AVAILABLE

The standby creation is logged as "Enable cross-region Autonomous Data Guard" even though both databases are in Jeddah — Oracle's internal name for a remote-tenancy peer. Check the swap:

POWERSHELL
oci db autonomous-database get --profile A_tenancy `
  --autonomous-database-id $env:PRIMARY_ADB_OCID `
  --query 'data.{name:"display-name", role:role, state:"lifecycle-state", switched:"time-of-last-switchover"}'

oci db autonomous-database get --profile B_tenancy `
  --autonomous-database-id <standby-ocid> `
  --query 'data.{name:"display-name", role:role, state:"lifecycle-state", switched:"time-of-last-switchover"}'

After the roles swap

  • Automatic backups and the primary's billing move to B_tenancy.
  • Applications reconnect to the B_tenancy database with its own wallet and network settings.
  • Only B's group has rights on A's database. Run all Data Guard operations as that group, or add the mirror pair (Endorse in A, Admit in B) so A's admins can act independently.

Problems I Hit and How to Recognize Them

SymptomCauseFix
404 NotAuthorizedOrNotFound; request_endpoint is MumbaiA database call made with the Mumbai (home-region) profile; the CLI ignores the region in the OCIDUse the Jeddah profile B_tenancy (or add --region me-jeddah-1)
401 NotAuthenticated at JeddahB_tenancy not subscribed to Jeddah, or identity not replicated yetSubscribe; wait ~15 minutes
409 "matching request still in progress"Clicked Subscribe twicePoll region-subscription list until READY
403 "go to your home region"IAM write sent to JeddahUse A_tenancy_frankfurt / B_tenancy_mumbai for policy writes
404 right after a policy editPolicy replication lagWait ~10 minutes and retry
404 on create with the target in MumbaiMumbai isn't a paired DR region for JeddahCreate in Jeddah, or in a region the source lists as a peer
CLI detailFix
oci iam policy update rejects --statements aloneAlso pass --version-date ""
A misspelt PowerShell variable gives no errorEcho every variable before use

OCI returns 404 rather than 403 for denied requests, so the response never confirms a resource exists. Read request_endpoint in every error first — it shows which region actually got the call.

Checklist

  1. Decide the target region: same region (as here) or a paired region from the source's Add peer database list.
  2. Subscribe the target tenancy to that region first.
  3. Know each tenancy's home region and have a profile for its IAM writes.
  4. Test authentication with oci os ns get --region <region>.
  5. Use the Jeddah profile (B_tenancy) for every database call and the home-region profile (B_tenancy_mumbai) for IAM writes; check request_endpoint in any error.
  6. Keep Endorse and Admit identical; use compartment OCIDs; wait after each IAM change.

Before Relying on It in an Outage

  • Download the standby's own wallet and set up its access control lists or private endpoint — network settings aren't copied from the source.
  • Recreate what applications need in B_tenancy: Vault secrets, DBMS_CLOUD credentials, buckets, database links.
  • Alarms on apply lag and on the standby leaving AVAILABLE; record a baseline lag.
  • Agree in writing who may declare a disaster — there's no automatic failover for a cross-tenancy standby.
  • Drill with a switchover or snapshot standby and time each phase.
  • For protection against a regional outage, add a second peer in a region paired with Jeddah, with the target tenancy subscribed there.
