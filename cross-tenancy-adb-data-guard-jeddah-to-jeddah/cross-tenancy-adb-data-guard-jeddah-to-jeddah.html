Cross-Tenancy Autonomous Data Guard with the OCI CLI: A Real Build, Jeddah to Jeddah

By Sunke Nithin · October 17, 2026   CLOUDOCIADBData Guard

The goal: an Autonomous Data Guard standby for the database CTRATP, in a different OCI tenancy and a different region. The Console can't configure a cross-tenancy standby, so everything is done with the OCI CLI from Windows PowerShell. The standby did get built — but in the same region as the primary, because the region pair I wanted turned out not to be supported. This is the full record, including six failures and what each one really meant.

Summary

  • Built: a cross-tenancy Autonomous Data Guard standby, Available, paired with the primary; a switchover was run to exercise the role swap.
  • Where: both databases are in Jeddah (me-jeddah-1). Jeddah → Mumbai is not a supported Autonomous Data Guard region pair, which was the real cause of the original failures.
  • Protects against: loss of a tenancy, accidental deletion, compartment or account compromise, database failure. Not against a Jeddah regional outage — that needs a standby in a region paired with Jeddah.
  • Time: about three hours, almost all of it on the six issues below.

Both profiles here use the same API key, uploaded to the user in each tenancy. That works, but remember it when rotating the key: replace it in both tenancies, or one profile silently stops authenticating.

Three Regions, and Which Call Goes to Each

Two tenancies, three regions — the root of most of the confusion. The final layout has both databases in Jeddah: the primary in A_tenancy and the standby in B_tenancy. Frankfurt is only where A_tenancy's IAM writes go, and Mumbai is B_tenancy's home region, where the standby was first attempted and refused because it isn't a paired DR region for Jeddah. B_tenancy therefore has to be subscribed to Jeddah, and its commands for Jeddah resources must carry --region me-jeddah-1. The CLI endpoint comes from the profile's region= or from --region, never from the region inside a resource OCID.

1CLI Profiles and Identifiers

C:\Users\<user>\.oci\config, one profile per tenancy (plus the Frankfurt one, see issue 4):

OCI CONFIG
[A_tenancy]
user=ocid1.user.oc1..<A-user-ocid>
fingerprint=<key-fingerprint>
tenancy=ocid1.tenancy.oc1..<A-tenancy-ocid>
region=me-jeddah-1
key_file=C:/Users/<user>/.oci/oci_api_key.pem

[A_tenancy_frankfurt]
# same user, tenancy and key as above - home region for IAM writes
region=eu-frankfurt-1

[B_tenancy]
user=ocid1.user.oc1..<B-user-ocid>
fingerprint=<key-fingerprint>
tenancy=ocid1.tenancy.oc1..<B-tenancy-ocid>
region=ap-mumbai-1
key_file=C:/Users/<user>/.oci/oci_api_key.pem

Prove authentication first — this call needs valid credentials and almost no permission, so it separates authentication from authorization:

POWERSHELL
oci os ns get --profile A_tenancy      # returns A's Object Storage namespace
oci os ns get --profile B_tenancy      # returns B's namespace

Collect the identifiers in PowerShell variables (note the backtick for line continuation, not Linux's backslash):

POWERSHELL
# Tenancy A, the primary
$env:SRC_TENANCY_OCID     = '<A-tenancy-ocid>'
$env:SRC_PRIMARY_CMP_OCID = '<primary-compartment-ocid>'
$env:PRIMARY_ADB_OCID = oci db autonomous-database list `
  --profile A_tenancy `
  --compartment-id $env:SRC_PRIMARY_CMP_OCID `
  --display-name 'CTRATP' `
  --query 'data[0].id' --raw-output

# Tenancy B, the standby side
$env:TGT_TENANCY_OCID     = '<B-tenancy-ocid>'
$env:TGT_STANDBY_CMP_OCID = '<operations-compartment-ocid>'

# echo every variable - PowerShell returns "" for a misspelt name
$env:PRIMARY_ADB_OCID
$env:TGT_STANDBY_CMP_OCID

Record the primary's shape — the standby inherits it. Check that it isn't Free Tier and uses no OCI Vault key (customer-managed keys aren't supported with a cross-tenancy standby):

POWERSHELL
oci db autonomous-database get --profile A_tenancy `
  --autonomous-database-id $env:PRIMARY_ADB_OCID `
  --query 'data.{name:"display-name", dbName:"db-name", state:"lifecycle-state",
           workload:"db-workload", ecpu:"compute-count", storage:"data-storage-size-in-gbs",
           license:"license-model", key:"key-store-id", free:"is-free-tier"}'

2IAM in B_tenancy (Standby Side)

B owns the group that does the work, so B needs permission to create the standby locally, and an Endorse stating what the group may do in A.

POWERSHELL
$env:DEST_GROUP_OCID = oci iam group create `
  --profile B_tenancy `
  --compartment-id $env:TGT_TENANCY_OCID `
  --name ADG-CrossTenancy-Admins `
  --description "Creates and manages the cross-tenancy ADG standby" `
  --query 'data.id' --raw-output

oci iam user-group-membership add --profile B_tenancy `
  --user-id <B-user-ocid> `
  --group-id $env:DEST_GROUP_OCID

Policy cross-tenancy-adb-adg in B's root compartment:

POLICY
Define tenancy SourceTenancy as <A-tenancy-ocid>
Allow group ADG-CrossTenancy-Admins to manage autonomous-database-family in compartment Operations
Endorse group ADG-CrossTenancy-Admins to manage autonomous-database-family in tenancy SourceTenancy
Endorse and Admit. Endorse goes in the tenancy that owns the group and says what the group may do elsewhere; Admit goes in the tenancy that owns the resource. Neither grants anything alone — the effective permission is the intersection. Define/Endorse/Admit are only valid in the root compartment; the group must actually contain the user; a top-level compartment can be named directly, a nested one needs its full path.

3IAM in A_tenancy (Primary Side)

A Admits B's group to the primary. This write must go to Frankfurt, A's home region — not Jeddah where the database is:

POLICY
Define tenancy DestinationTenancy as <B-tenancy-ocid>
Define group DestGroup as <ADG-CrossTenancy-Admins-group-ocid>
Admit group DestGroup of tenancy DestinationTenancy to manage autonomous-database-family in compartment id <primary-compartment-ocid>

The screenshots show an earlier revision with read autonomous-databases; both halves were later raised to manage autonomous-database-family (issue 6). Created with the Frankfurt profile:

POWERSHELL
$aPolicy = @(
  "Define tenancy DestinationTenancy as $env:TGT_TENANCY_OCID",
  "Define group DestGroup as $env:DEST_GROUP_OCID",
  "Admit group DestGroup of tenancy DestinationTenancy to manage autonomous-database-family in compartment id $env:SRC_PRIMARY_CMP_OCID"
)
$aPolicy | ConvertTo-Json | Set-Content -Encoding ascii a-policy.json

oci iam policy create --profile A_tenancy_frankfurt `
  --compartment-id $env:SRC_TENANCY_OCID `
  --name cross-tenancy-adb-adg-admit `
  --description "Admit B_tenancy's ADG group to the Jeddah primary" `
  --statements file://a-policy.json

# later updates need --statements and --version-date together
oci iam policy update --profile A_tenancy_frankfurt `
  --policy-id <admit-policy-ocid> `
  --statements file://a-policy.json `
  --version-date "" --force

Use compartment id <ocid> rather than a name: the primary's compartment is nested, so the name form would need the full Parent:Child:nslabs path. The OCID form can't be ambiguous.

4Prove the Cross-Tenancy Permission

This gate separates an IAM problem from a database problem. Read the Jeddah primary as B's group:

POWERSHELL
oci db autonomous-database get --profile B_tenancy `
  --region me-jeddah-1 `
  --autonomous-database-id $env:PRIMARY_ADB_OCID `
  --query 'data.{name:"display-name", state:"lifecycle-state", role:role}'

{
  "name": "CTRATP",
  "role": null,
  "state": "AVAILABLE"
}

B's group can see A's database across the tenancy boundary (role: null — no peer yet). --region me-jeddah-1 is mandatory: without it the call goes to Mumbai, which answers 404 exactly like a policy failure. If this fails, check credentials before policies:

POWERSHELL
# cheaper probe: are the credentials valid in that region at all?
oci os ns get --profile B_tenancy --region me-jeddah-1

After every policy edit, wait about ten minutes before retesting — retries run within seconds of a change test the old state.

5Create the Standby — First in Mumbai (Fails)

POWERSHELL
oci db autonomous-database create-cross-tenancy-disaster-recovery-details `
  --profile B_tenancy `
  --region ap-mumbai-1 `
  --compartment-id $env:TGT_STANDBY_CMP_OCID `
  --source-id $env:PRIMARY_ADB_OCID `
  --disaster-recovery-type ADG `
  --display-name "CTRATP-StandbyMumbai"

"code": "NotAuthorizedOrNotFound",
"status": 404,
"operation_name": "create_autonomous_database",
"request_endpoint": "POST https://database.ap-mumbai-1.oraclecloud.com/20160918/autonomousDatabases"

Only --compartment-id, --source-id and --disaster-recovery-type are required; the standby takes password, wallet, character set and sizing from the primary. Running with --debug showed a perfectly formed request (source type CROSS_TENANCY_DISASTER_RECOVERY, right OCIDs, right endpoint), and everything else was ruled out:

Wrong region on the commandRuled out — Mumbai is correct for the create

6Create the Standby in Jeddah (Works)

The same command, pointed at Jeddah instead of Mumbai:

POWERSHELL
oci db autonomous-database create-cross-tenancy-disaster-recovery-details `
  --profile B_tenancy `
  --region me-jeddah-1 `
  --compartment-id $env:TGT_STANDBY_CMP_OCID `
  --source-id $env:PRIMARY_ADB_OCID `
  --disaster-recovery-type ADG `
  --display-name "CTRATP-StandbyMumbai"
FieldValue
roleSTANDBY
lifecycle-statePROVISIONING → AVAILABLE
peer-db-idsthe primary CTRATP
disaster-recovery-typeADG
compartmentOperations, in B_tenancy
kms-key-idORACLE_MANAGED_KEY

What this proves: group, policies, source and target compartment were identical between the failing and the working attempt — only the target region changed. IAM was right all along; Autonomous Data Guard wouldn't accept Jeddah and Mumbai as a pair. (So the raise from read to manage may not have been needed; it was already in place, so the two can't be separated here.)

Careful when reading the result: dataguard-region-type: REMOTE_STANDBY_DG_REGION and disaster-recovery-region-type: REMOTE refer to the remote tenancy, not a remote region.

Why Mumbai was refused

The standby's Disaster recovery tab spells it out: "Local peer: 1, Cross-region peer: 0. You may create up to 1 local peer and 1 cross-region peer for every remote paired region that your tenancy is subscribed to." Each region has designated DR partner regions, normally in the same geography, and Mumbai isn't one of Jeddah's. To see the allowed regions, open the primary → Disaster recovery → Add peer database and look at the region list. A_tenancy is already subscribed to Riyadh (me-riyadh-1), the likely candidate for real regional DR.

7Verify

Provisioning took just under five minutes for a 2 ECPU / 20 GB database:

POWERSHELL
# standby, B_tenancy
oci db autonomous-database get --profile B_tenancy --region me-jeddah-1 `
  --autonomous-database-id <standby-ocid> `
  --query 'data.{role:role, state:"lifecycle-state", dg:"is-data-guard-enabled", peers:"peer-db-ids"}'

# primary, A_tenancy
oci db autonomous-database get --profile A_tenancy `
  --autonomous-database-id $env:PRIMARY_ADB_OCID `
  --query 'data.{role:role, peers:"peer-db-ids", dg:"is-data-guard-enabled"}'

# give it a name that matches where it lives
oci db autonomous-database update --profile B_tenancy --region me-jeddah-1 `
  --autonomous-database-id <standby-ocid> `
  --display-name "CTRATP-StandbyXTenancy-JED" --force

Each side should list the other in peer-db-ids; is-data-guard-enabled flips to true when provisioning completes. Rename the standby — a name that says Mumbai for a database in Jeddah will be misread during an incident. The Full Stack DR warning about missing policy permissions is harmless unless you use Full Stack DR.

8Switchover

POWERSHELL
oci db autonomous-database switchover --profile B_tenancy --region me-jeddah-1 `
  --autonomous-database-id <standby-ocid> `
  --peer-db-id $env:PRIMARY_ADB_OCID `
  --wait-for-state AVAILABLE

The standby creation is logged as "Enable cross-region Autonomous Data Guard" although both databases are in Jeddah — Oracle uses "cross-region" internally for a remote-tenancy peer.

After the roles swap

  • Automatic backups follow the primary role, so they start running in B_tenancy — and so does the primary's billing.
  • Applications must reconnect to the B_tenancy database with its own wallet and network settings.
  • The policies only let B's group act on A's database. Keep running all Data Guard operations as that group, or build the mirror pair (Endorse in A, Admit in B) so A's admins can act on their own.

Reading OCI Error Codes

CodeMeaningWhere to look
404 NotAuthorizedOrNotFoundThe endpoint denies access or can't see the resourceA missing --region; otherwise a real policy gap
401 NotAuthenticatedThe region can't validate your credentialsRegion subscription or identity replication — not policies
403 NotAllowed, "home region"IAM write sent to a non-home regionUse a profile for the home region
409 request in progressDuplicate of a running requestStop and poll

OCI returns 404 instead of 403 for denied reads on purpose, so a denial can't prove a resource exists. Always read request_endpoint first.

Pre-Flight Checklist for the Next Build

  1. Check the region pair first — primary → Disaster recovery → Add peer database shows the allowed regions. No policy works around an unsupported pair.
  2. Check region subscriptions in both tenancies; the standby tenancy must be subscribed to the primary's region. Start this first — it's permanent and can take up to an hour.
  3. Find each tenancy's home region and create the profile for IAM writes up front.
  4. Prove authentication with oci os ns get --profile <p> --region <r> in every region you'll touch.
  5. Pass --region on every command for a resource outside the profile's region.
  6. Wait after every IAM change.
  7. Use compartment id <ocid> in policies.
  8. Echo every shell variable before using it.
  9. Keep Endorse and Admit identical in verb and resource type.
  10. Change one thing at a time and verify it landed.

Before Relying on It in an Outage

  • Download the standby's own wallet; configure its access control lists or private endpoint — network settings aren't replicated.
  • Recreate what applications depend on: Vault secrets, DBMS_CLOUD credentials, buckets, database links, scheduler endpoints.
  • Create alarms on apply lag and on the standby leaving AVAILABLE; record a baseline lag.
  • Build the mirror-image policies, and agree in writing who may declare a disaster — there is no automatic failover for a cross-tenancy standby.
  • Drill with a snapshot standby and time each phase; put the measured time in the DR plan.
  • For regional DR, add a peer in a region paired with Jeddah, with the standby tenancy subscribed there.

Open questions to confirm against Oracle documentation: whether read or manage is really required on the source (serverless and dedicated docs differ), whether customer-managed keys work with a cross-tenancy standby, and the current published RPO/RTO.
