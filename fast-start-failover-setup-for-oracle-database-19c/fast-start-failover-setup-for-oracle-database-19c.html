Fast-Start Failover Setup for Oracle Database 19c

By Sunke Nithin · December 10, 2024   DatabaseOracleData Guard

Fast-Start Failover (FSFO) makes Data Guard fail over automatically: an observer process on a separate host watches the primary and standby, and if the primary is lost it promotes the standby — no DBA needed at 3 a.m. This is the full cycle on 19c: prepare, set up the observer host, configure and enable FSFO, test it, reinstate the old primary, switch back, and finally switch it off again.

Primary ⇄ Standby (SYNC redo) · Observer on a third host pings both

Pre-Checks

  • A working Data Guard configuration (see physical standby with active duplicate) managed by the broker (broker setup).
  • Enterprise Edition.
  • Flashback Database on both databases, so the failed primary can be reinstated automatically.
  • Network access from the observer host to both databases.
SQL
-- on primary and standby
select force_logging, flashback_on, protection_mode from v$database;
alter database flashback on;              -- standby: stop redo apply first
alter system set dg_broker_start=true;

1Prepare the Observer Host

Install the Oracle Database 19c Client with the Administrator installation type — it includes dgmgrl. Add tnsnames entries for both databases and check them:

BASH
# observer host: Oracle Client 19c, Administrator install type (includes dgmgrl)
$ cat ~/profile_client
export ORACLE_HOME=/u01/app/oracle/product/19c_cl1
export PATH=$ORACLE_HOME/bin:$PATH

$ tnsping <primary_alias>
$ tnsping <standby_alias>

For a background observer, store SYS credentials in a wallet so it can log in unattended — the steps are in Configuring the FSFO observer.

2Protection Mode

For zero data loss, run synchronous transport in MaxAvailability (my databases already were):

DGMGRL
DGMGRL> show configuration;

-- zero-data-loss FSFO: synchronous transport + MaxAvailability
DGMGRL> edit database <primary> set property LogXptMode='SYNC';
DGMGRL> edit database <standby> set property LogXptMode='SYNC';
DGMGRL> edit configuration set protection mode as MaxAvailability;

In MaxPerformance mode FSFO also works, limited by FastStartFailoverLagLimit — it fails over only if the standby is within that many seconds of the primary.

3Set the FSFO Targets

DGMGRL
DGMGRL> edit database <primary> set property FastStartFailoverTarget='<standby>';
DGMGRL> edit database <standby> set property FastStartFailoverTarget='<primary>';
DGMGRL> edit configuration set property FastStartFailoverThreshold=30;
DGMGRL> edit configuration set property FastStartFailoverAutoReinstate=TRUE;

4Start the Observer and Enable FSFO

DGMGRL
DGMGRL> start observer obs1 in background
          file is '/u01/app/oracle/fsfo/fsfo.dat'
          logfile is '/u01/app/oracle/fsfo/fsfo.log'
          connect identifier is <primary>;
DGMGRL> enable fast_start failover;
DGMGRL> show fast_start failover;
DGMGRL> show configuration;
...
Fast-Start Failover: Enabled in Zero Data Loss Mode

5Test: Kill the Primary

Killing the PMON process simulates an instance crash (a SHUTDOWN ABORT works too; a normal shutdown does not trigger FSFO):

BASH
# primary host: simulate an instance crash
ps -ef | grep [p]mon_<SID>
kill -9 <pmon_pid>

# observer host
tail -f /u01/app/oracle/fsfo/fsfo.log
... Primary database cannot be reached.
... Fast-Start Failover threshold has expired.
... Initiating Fast-Start Failover to database "<standby>"...
... Failover succeeded, new primary is "<standby>"

6Reinstate the Failed Primary

SQL
-- old primary host: start the failed database
SQL> startup mount
-- the observer reinstates it as a standby (needs Flashback Database)
... Reinstatement of database "<primary>" succeeded

DGMGRL> show configuration;      -- roles swapped, status SUCCESS

7Switch Back

DGMGRL
DGMGRL> switchover to <primary>;   -- back to the original roles

8Disabling FSFO and Removing the Observer

For maintenance, or before decommissioning the observer host:

DGMGRL
DGMGRL> disable fast_start failover;
DGMGRL> stop observer obs1;
DGMGRL> show observer;

Then remove the observer's wallet and files and decommission the host.

Run the observer where it shares no single point of failure with either database — ideally a third site. In 19c you can run up to three observers; one is the master and the others take over if it fails.
