OCI IAM in Practice: Compartments, Groups and Policies for Two Project Teams

By Sunke Nithin · December 16, 2019   CLOUDOCISecurity

How do OCI users, groups, compartments and policies fit together? This walk-through sets up a realistic company — SunkeTech — with a shared network run by a network admin, and two project teams that each manage their own servers but can't touch each other's or the network.

The Requirements

  • One VCN for both teams, managed only by a network administrator.
  • Project A and Project B each have their own instances and block volumes, and can't use each other's.
  • Neither team may change the VCN.
  • Each team has its own administrators, who decide who in their team gets access.

The Design

CompartmentHolds
Network_compThe shared VCN, subnets, gateways
Project_A_compProject A instances and volumes
Project_B_compProject B instances and volumes
GroupMembers (example)Role
AdministratorsmarkTenancy administrators (exists by default)
Network_AdminsalexBuild and run the VCN
Project_A_Admins / Project_B_Adminsjack / malinaManage everything in their project compartment
Project_A_Users / Project_B_Userslara / lisaUse (start, stop) existing instances and volumes

Compartment and group names can contain letters, digits, hyphens, underscores and periods — no spaces — so use names like Project_A_comp consistently in the console and in policies.

1Starting Point

Signing up creates the tenancy (the root compartment), your first user, the Administrators group and the Tenant Admin Policy: Allow group Administrators to manage all-resources in tenancy.

2Create the Compartments

Identity & Security → Compartments → Create Compartment, three times, under the root: Network_comp, Project_A_comp, Project_B_comp.

3Create the Groups

Identity & Security → Domains → (your domain) → Groups → Create group: Network_Admins, Project_A_Admins, Project_B_Admins, Project_A_Users, Project_B_Users.

4Write the Policies

Identity & Security → Policies → Create Policy in the root compartment (statements about the tenancy must live there):

POLICY
-- network administrators
Allow group Network_Admins to manage virtual-network-family in compartment Network_comp
Allow group Network_Admins to manage instance-family in compartment Network_comp

-- project admins may use (not change) the shared VCN
Allow group Project_A_Admins, Project_B_Admins to use virtual-network-family in compartment Network_comp

-- project admins fully manage their own compartment
Allow group Project_A_Admins to manage all-resources in compartment Project_A_comp
Allow group Project_B_Admins to manage all-resources in compartment Project_B_comp

-- project admins manage membership of their own users group only
Allow group Project_A_Admins to use users  in tenancy where target.group.name='Project_A_Users'
Allow group Project_A_Admins to use groups in tenancy where target.group.name='Project_A_Users'
Allow group Project_B_Admins to use users  in tenancy where target.group.name='Project_B_Users'
Allow group Project_B_Admins to use groups in tenancy where target.group.name='Project_B_Users'

-- everyone in a project can see the list of users and groups
Allow group Project_A_Users, Project_B_Users to inspect users  in tenancy
Allow group Project_A_Users, Project_B_Users to inspect groups in tenancy

5Create Users and Add Them to Groups

Users → Create user for jack, malina, lara, lisa, mark and alex; open each group → Assign user to groups. New users receive an email to set their password (or an admin resets it); they must change it at first sign-in.

6Network Admin Builds the VCN

Signed in as alex, in Network_comp: create the VCN with an internet gateway, a route table with 0.0.0.0/0 → internet gateway, a public subnet and its security list. Alex can also launch a test VM there, because his group may manage instances in that compartment. Terminate it after testing.

7Project Admins Launch Instances

jack launches an instance in Project_A_comp, attached to the shared subnet; malina does the same in Project_B_comp. Each can see and manage only their own compartment.

Compartments are about permissions, not network isolation. Two instances in the same subnet can reach each other even if they're in different compartments — my original post expected them not to ping each other. To isolate the projects on the network, give each its own subnet (or VCN) with security lists, or use network security groups that allow traffic only within the project.

8Rights for Project Users

POLICY
Allow group Project_A_Users to use instance-family in compartment Project_A_comp
Allow group Project_A_Users to use volume-family   in compartment Project_A_comp
Allow group Project_A_Users to inspect virtual-network-family in compartment Network_comp

Allow group Project_B_Users to use instance-family in compartment Project_B_comp
Allow group Project_B_Users to use volume-family   in compartment Project_B_comp
Allow group Project_B_Users to inspect virtual-network-family in compartment Network_comp

Signed in as lara: she can start, stop and reboot Project A's instances, but trying to create a VCN or launch a new instance fails with an authorization error. Launching needs use on the subnet and VNICs, which only the admins have.

What This Shows

  • Policies grant access to groups, never directly to users.
  • Compartments set the scope; the verbs inspect < read < use < manage set the power.
  • Conditions (where target.group.name=...) let team admins manage their own team without becoming tenancy admins.

Based on the "Example Scenario" in Oracle's OCI IAM documentation, carried out in my own tenancy. Related: User, group and policy for Terraform.
