Understanding Oracle GoldenGate: Architecture, Purpose and Use Cases

By Sunke Nithin · April 27, 2025   ReplicationOracleGoldengate

Oracle GoldenGate (OGG) is a real-time data replication and integration tool. It captures changes as they happen in a source database and applies them to a target database almost immediately. Because it reads the database's redo / transaction logs rather than querying tables, it puts very little load on the source.

1GoldenGate Architecture

GoldenGate is built from five main components:

ComponentPurpose
ManagerControls the startup, shutdown and monitoring of the other processes.
ExtractCaptures (reads) changes from the source database — from the logs, not from the tables directly.
Data Pump(Optional) A secondary Extract that moves trail files across the network securely and efficiently.
Trail FilesIntermediate files that store the captured changes until they are applied.
ReplicatApplies the changes to the target database.

Think of it like this:

ExtractCapture
TrailStore
PumpMove
ReplicatApply
This describes GoldenGate's Classic Architecture. In the newer Microservices Architecture (the default from 19c/21c onwards), the same Extract → trail → Replicat flow runs under a web-managed Service Manager, and the Data Pump role is handled by the Distribution and Receiver services.

2Purpose of GoldenGate

  • Real-time replication: keep two databases in sync with very low lag — seconds or less.
  • Near-zero-downtime migrations: move from an old database to a new one without taking applications offline for the copy.
  • High availability: maintain a live standby database ready for quick failover.
  • Data distribution: feed real-time data into reporting systems, cloud warehouses or analytics tools.
  • Heterogeneous replication: replicate between different database types (e.g. Oracle → MySQL).

4Case Study: E-commerce Database Migration with GoldenGate

Background

A large e-commerce company — let's call it ShopABC — runs its online store on an Oracle 12c database. It wants to migrate to Oracle 19c on Oracle Cloud (OCI), but:

  • It can't afford a long outage — the website must stay online 24×7.
  • It needs real-time synchronization during the migration.
  • It wants a failback option in case something goes wrong.

Solution: Using Oracle GoldenGate

  1. Set up GoldenGate on both sides
    • Install GoldenGate on the on-premises 12c server and the 19c cloud server.
    • Configure Extract on the source and Replicat on the target.
  2. Perform the initial load
    • Bulk-copy all existing data from 12c to 19c — with a GoldenGate initial-load task, or Data Pump export/import from a consistent SCN.
  3. Enable change data capture (CDC)
    • Extract continuously reads new changes (new orders, customer updates) from the redo logs.
    • Replicat applies them to the 19c cloud database in near real time.
  4. Monitor synchronization
    • Watch replication lag and process checkpoints (for example with INFO ALL and LAG REPLICAT in GGSCI) until the target is consistently caught up.
  5. Final switchover
    • Pick a low-traffic time (e.g. 2 AM).
    • Stop the application briefly (perhaps 10–15 minutes), let Replicat apply the last changes, then point the application at the new cloud database.
    • Resume operations on 19c.
  6. Decommission the old environment
    • After confirming everything works, shut down the old 12c system.
Failback: to be able to fall back after switchover, set up reverse replication (Extract on 19c, Replicat on 12c) before the application moves. That keeps the old 12c database current with changes made on 19c until you're confident enough to decommission it.

✅ Key Takeaways

  • GoldenGate is one of the leading tools for near-zero-downtime migrations.
  • It doesn't just copy data — it keeps syncing live changes until you cut over.
  • Administrators watch lag and checkpoints closely.
  • Real-world GoldenGate projects usually follow Initial Load → Live Sync → Final Cutover.
