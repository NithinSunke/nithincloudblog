Configuring a Cascaded Standby in Oracle Data Guard 19c

By Sunke Nithin · August 8, 2022   DatabaseOracleData Guard

A cascaded standby receives its redo not from the primary but from another standby. The primary ships redo once, and the first standby forwards it — useful for a far-away DR site or a reporting copy, without extra load on the primary's network. Here NPGRSB1 is added behind the existing standby NPGRSB.

NPGR (primary) → NPGRSB (standby) → NPGRSB1 (cascaded standby)

Starting point: primary and standby built with RMAN active duplicate, managed by the Data Guard broker.

1Listener on the Cascade Host

A static entry for the duplicate and one for the broker (on RAC/ASM hosts, add these to the Grid home's listener):

LISTENER.ORA
LISTENER =
  (DESCRIPTION_LIST =
    (DESCRIPTION =
      (ADDRESS = (PROTOCOL = TCP)(HOST = rac1.snvcloud.com)(PORT = 1522))
      (ADDRESS = (PROTOCOL = IPC)(KEY = EXTPROC1522))
    )
  )

SID_LIST_LISTENER =
  (SID_LIST =
    (SID_DESC = (GLOBAL_DBNAME = NPGRSB1)        (ORACLE_HOME = /h01/oracle/19cr3) (SID_NAME = NPGRSB1))
    (SID_DESC = (GLOBAL_DBNAME = NPGRSB1_DGMGRL) (ORACLE_HOME = /h01/oracle/19cr3) (SID_NAME = NPGRSB1))
  )

2Net Entries on All Three Servers

TNSNAMES.ORA
NPGRSB1 =
  (DESCRIPTION =
    (ADDRESS = (PROTOCOL = TCP)(HOST = rac1.snvcloud.com)(PORT = 1522))
    (CONNECT_DATA = (SERVER = DEDICATED)(SERVICE_NAME = NPGRSB1))
  )
# plus the existing NPGR and NPGRSB entries - on all three servers

tnsping npgr; tnsping npgrsb; tnsping npgrsb1

3Let the Configuration Include the New Database

SQL
-- primary and first standby: allow the third database
alter system set log_archive_config='DG_CONFIG=(NPGR,NPGRSB,NPGRSB1)';

4Prepare and Start the Auxiliary Instance

BASH
# on the cascade host
mkdir -p /h01/oracle/admin/NPGRSB1/adump /h01/oracle/oradata/NPGRSB1 /h01/oracle/fast_recovery_area/NPGRSB1
scp orstsbdvl01:/h01/oracle/19cr3/dbs/orapwNPGRSB /h01/oracle/19cr3/dbs/orapwNPGRSB1
echo "DB_NAME=NPGR" > /h01/oracle/19cr3/dbs/initNPGRSB1.ora
export ORACLE_SID=NPGRSB1
echo startup nomount | sqlplus -s / as sysdba

5Duplicate from the First Standby

Using the standby as the source keeps the copy load off the primary:

RMAN
rman target sys@npgrsb auxiliary sys@npgrsb1     # duplicate FROM the first standby

DUPLICATE TARGET DATABASE
  FOR STANDBY
  FROM ACTIVE DATABASE
  DORECOVER
  SPFILE
    SET db_unique_name='NPGRSB1' COMMENT 'Cascaded standby'
    SET control_files='/h01/oracle/oradata/NPGRSB1/control01.ctl','/h01/oracle/fast_recovery_area/NPGRSB1/control02.ctl'
    SET audit_file_dest='/h01/oracle/admin/NPGRSB1/adump'
    SET db_create_file_dest='/h01/oracle/oradata'
    SET db_recovery_file_dest='/h01/oracle/fast_recovery_area'
    SET log_archive_dest_2=''
    SET fal_server='NPGRSB'
  NOFILENAMECHECK;

Start redo apply on NPGRSB1 if the broker doesn't (alter database recover managed standby database disconnect;).

6Add It to the Broker and Set Redo Routes

With the broker in charge, don't set LOG_ARCHIVE_DEST_n for cascading by hand — the broker owns those parameters and will overwrite or conflict with them. The 12.2+ way is the RedoRoutes property:

DGMGRL
$ dgmgrl sys@npgr
DGMGRL> add database npgrsb1 as connect identifier is npgrsb1 maintained as physical;

-- redo routes: primary -> npgrsb, npgrsb -> npgrsb1
DGMGRL> edit database npgr   set property RedoRoutes='(LOCAL : npgrsb ASYNC)';
DGMGRL> edit database npgrsb set property RedoRoutes='(npgr : npgrsb1 ASYNC)';
DGMGRL> enable database npgrsb1;
DGMGRL> show configuration;
OUTPUT
Configuration - my_dg_config

  Protection Mode: MaxPerformance
  Members:
  npgr    - Primary database
    npgrsb  - (*) Physical standby database
      npgrsb1 - Physical standby database (receiving current redo)

Fast-Start Failover: ENABLED

Configuration Status:
SUCCESS

Before the route was set, my configuration showed ORA-16810/ORA-16829 warnings and the new database as disabled; they cleared once it was enabled and routing was in place.

If the Middle Standby Goes Down

NPGRSB1 stops receiving redo. Route around it from the primary until it's back:

DGMGRL
-- if npgrsb is lost, let the primary ship directly to npgrsb1
DGMGRL> edit database npgr set property RedoRoutes='(LOCAL : npgrsb ASYNC, npgrsb1 ASYNC)';
A cascaded standby is always a little behind the first standby and isn't a valid target for Fast-Start Failover. In 19c it can receive redo in real time from the cascading standby (as shown by receiving current redo).
