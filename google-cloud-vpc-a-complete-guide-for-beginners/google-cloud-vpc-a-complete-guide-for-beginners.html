Google CLOUD VPC: A Complete Guide for Beginners

By Sunke Nithin · August 9, 2025   CLOUDGCP

A Virtual Private Cloud (VPC) is your own private, isolated network inside Google Cloud. Every VM, GKE cluster and internal load balancer is attached to one. This guide covers the building blocks — subnets, routes, firewall rules, peering, Shared VPC and hybrid connectivity — with gcloud examples.

What Makes a GCP VPC Different

In GCP a VPC is global: one network spans every region, and VMs in different regions talk over Google's backbone using internal IPs, with no extra setup. Its subnets are regional — each has an IP range and lives in one region, across all of that region's zones.

Core Components

1. Subnets

  • Regional, each with a primary IPv4 range (and optional secondary ranges for alias IPs / GKE).
  • Ranges must not overlap within the VPC or with peered networks.
  • A subnet can be expanded later, but never shrunk — see Extend a subnet in GCP.

2. Routes

  • Each subnet gets an automatic route so all subnets can reach each other.
  • A new VPC also gets a default route 0.0.0.0/0 to the default internet gateway. A VM only actually reaches the internet through it if it has an external IP or uses Cloud NAT.
  • Add custom static routes, or dynamic routes learned by Cloud Router (BGP) from VPN/Interconnect.

3. Firewall Rules

  • Stateful: replies to allowed traffic are allowed automatically.
  • Defined on the VPC, but enforced at each VM — and they can target all instances, network tags, or service accounts.
  • Both allow and deny rules exist for ingress and egress; the lowest priority number wins.
  • Two implied rules you can't delete: allow all egress and deny all ingress (both at the lowest priority, 65535).

4. VPC Network Peering

  • Private RFC 1918 connectivity between two VPCs, in the same or different projects or organizations.
  • Must be configured from both sides; ranges can't overlap.
  • Not transitive: if A peers with B and B with C, A cannot reach C through B.

5. Shared VPC

  • A host project owns the VPC; service projects deploy resources into its subnets.
  • Network admins keep central control of subnets, routes and firewalls while application teams manage their own projects and billing.

6. Cloud NAT, Cloud VPN, Cloud Interconnect

  • Cloud NAT — outbound internet for VMs without external IPs; nothing can connect in.
  • Cloud VPN — IPsec tunnels to on-premises or another CLOUD over the internet (HA VPN gives a 99.99% SLA).
  • Cloud Interconnect — a dedicated or partner physical link for high bandwidth and predictable latency.

Create a VPC

Console

  1. Open VPC networks → Create VPC network.
  2. Name my-custom-vpc, subnet creation mode Custom.
  3. Add a subnet: name web-subnet, region us-central1, range 10.10.10.0/24.
  4. Click Create.

A screenshot walk-through is in Create a VPC in GCP: step by step.

gcloud

BASH
gcloud compute networks create my-custom-vpc \
  --subnet-mode=custom

gcloud compute networks subnets create web-subnet \
  --network=my-custom-vpc \
  --region=us-central1 \
  --range=10.10.10.0/24

Firewall Rule Examples

BASH
gcloud compute firewall-rules create allow-http \
  --network=my-custom-vpc \
  --direction=INGRESS \
  --allow=tcp:80 \
  --source-ranges=0.0.0.0/0 \
  --target-tags=http-server

This lets HTTP in from anywhere, but only to VMs with the network tag http-server — appropriate for a public web server, and nothing else is opened.

BASH
# egress deny rules exist too: block outbound SMTP from every VM
gcloud compute firewall-rules create deny-smtp-egress \
  --network=my-custom-vpc \
  --direction=EGRESS \
  --action=DENY \
  --rules=tcp:25 \
  --destination-ranges=0.0.0.0/0 \
  --priority=900

VPC Peering Example

BASH
# peering must be created from BOTH sides before it becomes ACTIVE
gcloud compute networks peerings create peer-1-to-2 \
  --network=vpc-1 \
  --peer-network=vpc-2

gcloud compute networks peerings create peer-2-to-1 \
  --network=vpc-2 \
  --peer-network=vpc-1

# for a VPC in another project add  --peer-project=<project-id>
gcloud compute networks peerings list

Once both sides exist the state changes to ACTIVE and subnet routes are exchanged automatically.

Key Concepts

Global VPCOne network across all regions; subnets are regional
CIDRAddress ranges such as 10.0.0.0/16 that define subnets
Custom vs auto modeCustom: you create the subnets. Auto: one subnet per region from 10.128.0.0/9
Firewall rulesStateful allow/deny, ingress/egress, targeted by tags or service accounts

Cloud NATOutbound internet without external IPs

Best Practices

  1. Use custom-mode VPCs; keep the auto-mode default network for quick tests only.
  2. Plan non-overlapping ranges with on-premises and other clouds before you build.
  3. Separate environments (dev, test, prod) — by subnet at least, ideally by VPC or project.
  4. Target firewall rules with network tags or service accounts; avoid 0.0.0.0/0 sources except for public services.
  5. Give VMs internal IPs only and use Cloud NAT / IAP — see Private Google Access and Cloud NAT.
  6. Control who can change networks with IAM (roles/compute.networkAdmin, roles/compute.securityAdmin).
  7. Turn on VPC Flow Logs on important subnets, and keep Admin Activity audit logs.

Example Company Layout

  • prod-vpc with subnets in us-east1 and europe-west1.
  • Separate subnets for frontend, backend and database tiers, with firewall rules allowing only the flows between them.
  • Cloud NAT for outbound updates; no external IPs on backend or database VMs.
  • Peering between prod-vpc and a monitoring-vpc so monitoring reaches the servers privately.

Summary

The VPC is the backbone of everything you run in GCP. Get the address plan, firewall model and connectivity right at the start, and the rest of the platform builds cleanly on top of it.
