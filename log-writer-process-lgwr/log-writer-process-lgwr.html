Log Writer Process (LGWR)

By Sunke Nithin · October 29, 2020   DatabaseOracle

Every change made in an Oracle database is first recorded as redo in the redo log buffer in the SGA. The log writer (LGWR) background process writes that redo to the online redo log files on disk — and it's that write, not the write of the data blocks, that makes a commit durable.

Server process makes a changeRedo copied into the redo log bufferLGWR writes it to the online redo logCommit acknowledgedDBWn writes data blocks later

What LGWR Writes, and When

The redo log buffer is circular: once LGWR has written a stretch of it to disk, server processes can reuse that space. LGWR writes one contiguous chunk of the buffer each time — everything copied in since its last write. It writes when:

TriggerWhy
A transaction commitsThe commit record and that transaction's redo must be on disk before the commit returns
Every three secondsSo redo never sits in memory for long
The buffer is one-third full (or holds about 1 MB of redo)To keep free space for new entries
Before DBWn writes changed blocksWrite-ahead logging — see below
At a log switchThe current log is completed before moving to the next group

Write-Ahead Logging

Before the database writer (DBWn) writes a changed block to a data file, all the redo describing that change must already be in the online redo log. If DBWn finds redo that isn't written yet, it asks LGWR to write it and waits. This guarantees that after a crash, every change in the data files can be rolled forward or back from the redo.

Fast Commit

When a user commits, LGWR writes the commit record and the transaction's redo to disk immediately, but the changed data blocks stay in the buffer cache to be written later, when it's efficient. The commit is complete the moment that redo write finishes — Oracle returns success even though the data files haven't been updated. If the instance crashes, instance recovery replays the redo.

The commit is also given a system change number (SCN), recorded with the redo. SCNs order all changes, which is what lets recovery — and RAC instances and distributed transactions — stay consistent.

LGWR sometimes writes redo for transactions that haven't committed yet, for example when buffer space is needed. That's fine: the changes only become permanent if the transaction later commits; otherwise recovery rolls them back using undo.

Group Commits

Under heavy load, while LGWR is busy writing one commit, other sessions commit too and must wait for that write to finish. LGWR then writes all of their redo in a single I/O. One write carrying many commit records means far less I/O than one per transaction, so throughput rises as concurrency rises.

Multiplexed Redo Logs

Each online redo log group should have at least two members on different disks. LGWR writes to all members of the current group at the same time:

  • If one member is damaged or unavailable, LGWR keeps writing to the others and records the error in its trace file and the alert log.
  • If all members of the group are unavailable, LGWR can't continue and the instance stops.
  • LGWR also can't reuse a group that hasn't been archived yet (in ARCHIVELOG mode) — the database waits until archiving catches up, so size and number your groups accordingly.

Since Oracle 12c: LGWR Workers

From 12c, LGWR can use helper processes: a log writer coordinator and LGnn worker processes that write in parallel, which helps on systems with many CPUs and heavy redo. LGWR also switches adaptively between two ways of telling sessions their commit is done — post/wait and polling — depending on which gives lower latency.

SQL
-- LGWR and its helper processes (12c+)
SELECT pname, description FROM v$process WHERE pname LIKE 'LG%' ORDER BY pname;

-- redo log groups and members
SELECT l.group#, l.thread#, l.sequence#, l.bytes/1024/1024 AS mb, l.status, l.archived, f.member
  FROM v$log l JOIN v$logfile f ON f.group# = l.group#
 ORDER BY l.group#;

Monitoring LGWR

Two wait events tell you whether redo writing is a bottleneck:

Wait eventWho waitsMeaning
log file syncUser sessions at commitTotal commit time — includes LGWR's write plus CPU scheduling and posting
log file parallel writeLGWRPure I/O time to write to the redo log files

If log file sync is high but log file parallel write is low, the problem is CPU or commit frequency, not storage. If both are high, look at the redo log disks.

SQL
-- commit latency as seen by sessions vs. LGWR's own write time
SELECT event, total_waits, ROUND(time_waited_micro/NULLIF(total_waits,0)/1000, 2) AS avg_ms
  FROM v$system_event
 WHERE event IN ('log file sync', 'log file parallel write');

-- how many log switches per hour
SELECT TO_CHAR(first_time, 'YYYY-MM-DD HH24') AS hour, COUNT(*) AS switches
  FROM v$log_history
 WHERE first_time > SYSDATE - 1
 GROUP BY TO_CHAR(first_time, 'YYYY-MM-DD HH24')
 ORDER BY 1;

Tips

  • Put redo logs on fast, low-latency storage, separate from data files where possible.
  • Size redo logs so switches happen every 15–20 minutes at peak — frequent switches mean frequent checkpoints.
  • Avoid committing every row in batch loads; commit in sensible batches.
