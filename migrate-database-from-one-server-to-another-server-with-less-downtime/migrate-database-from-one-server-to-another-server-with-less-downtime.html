Migrate a Database to Another Server with Less Downtime

By Sunke Nithin · August 3, 2022   DatabaseOracleMigration

To move a database to a new server (same OS platform and Oracle version) with a short outage, restore an RMAN backup on the new server ahead of time and keep it rolled forward with archived logs from the source. At cutover you only apply the last few logs and open the database. Downtime is minutes instead of the time a full backup and restore takes.

This is essentially a manual standby database. If you can, a Data Guard physical standby does the log shipping and applying for you, and a switchover gives the same result.

1Back Up the Source

RMAN
RMAN> backup database plus archivelog;
RMAN> backup current controlfile;

2Copy the Backup to the New Server

BASH
scp -p /backup/FTEX/full/* oracle@orstsbdvl01:/backup/FTEX/full/

3Prepare the New Server

  • Copy the pfile (or create one from the spfile with create pfile from spfile) and the password file to $ORACLE_HOME/dbs.
  • Create every directory the pfile refers to — control files, audit_file_dest, data file paths, FRA. With different paths, use SET NEWNAME in the restore.
  • Add an /etc/oratab entry.

4Start the Instance in NOMOUNT

SQL
SQL> startup nomount
ORACLE instance started.

Total System Global Area 1870647296 bytes
Fixed Size                  2254304 bytes
Variable Size             520096288 bytes
Database Buffers         1342177280 bytes
Redo Buffers                6119424 bytes
SQL> exit

5Restore and Recover

RMAN
RMAN> run {
  allocate channel d1 type disk;
  restore controlfile from '/backup/FTEX/full/c-2959031005-20220803-00';
  sql 'alter database mount';
  catalog start with '/backup/FTEX/' noprompt;
  restore database;
  recover database;
}

recover database stops with an error asking for an archived log that doesn't exist yet — that's expected. Don't open the database; leave it mounted.

6Keep It Rolled Forward

Repeat hourly or daily: copy the new archived logs and apply them.

BASH
# on the source: copy the new archived logs
scp -p /h01/oracle/fast_recovery_area/FTEX/archivelog/2022_08_03/* \
    oracle@orstsbdvl01:/h01/oracle/fast_recovery_area/FTEX/archivelog/2022_08_03/

# on the target: register them and roll forward
RMAN> catalog start with '/h01/oracle/fast_recovery_area/FTEX/archivelog/' noprompt;
RMAN> recover database;
The restored control file doesn't know about logs archived after the backup, so catalog them before each recovery — otherwise recover database won't find them even though they're in the FRA directory.

7Cutover

Stop the applications, archive the current redo log, and shut the source down:

SQL
-- on the source
SQL> alter system archive log current;
SQL> shutdown immediate

Copy the last archived logs to the new server, catalog, recover and open:

BASH
scp -p /h01/oracle/fast_recovery_area/FTEX/archivelog/2022_08_03/* \
    oracle@orstsbdvl01:/h01/oracle/fast_recovery_area/FTEX/archivelog/2022_08_03/
RMAN
RMAN> catalog start with '/h01/oracle/fast_recovery_area/FTEX/archivelog/' noprompt;
RMAN> recover database;
SQL> alter database open resetlogs;
Archive the current log before shutting down — in my original order (shut down first, then copy) the changes in the last online redo log would have been lost.

8Switch the Applications

Point the applications at the new server (or move the DNS name / VIP), validate, and take a fresh full backup — the old backups belong to the previous incarnation.
