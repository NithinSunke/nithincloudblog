OCI – Patching a DB System (VM / Bare Metal) Made Simple

By Sunke Nithin · April 4, 2025   DatabaseOracleOCIPatching

Keeping databases patched is a core DBA job, and in Oracle Cloud Infrastructure (OCI) the tooling on a Base Database Service DB system does most of the work. This post covers the patch types, a pre-patch checklist, and patching a DB system from 19.23 to 19.24 with dbcli — Grid Infrastructure first, then the database home.

What Is a DB System?

A DB system is a non-autonomous Oracle Database on an OCI virtual machine or bare metal server (the Base Database Service). Unlike Autonomous Database, you decide when to patch — Oracle provides the patches and the tooling.

Patch Types

PatchWhat it updatesHow
DB system patchGrid Infrastructure and the cloud tooling (DCS agent) on the hostConsole → DB system → Updates, or dbcli update-server
Database home patchThe Oracle Database binaries in a DB home, then datapatch for each databaseConsole → Database home → Updates, or dbcli update-dbhome
Release Updates (RU)The quarterly bug-fix and security bundle — what both of the above applyOffered in the console once Oracle publishes it for OCI
One-off patchesFixes for specific bugs from My Oracle SupportApply with OPatch, or via custom database software images
OS updatesOracle Linux packagesSeparate — OS updates from the DB system's Updates page; not part of the DB system patch
Correction: my original table said a DB system patch covers "OS and grid infrastructure". It patches GI and the tooling; operating system updates are a separate step.

Pre-Patching Checklist

  • A recent backup (OCI automatic backup or RMAN) — and you know how to restore it.
  • Enough free space on /u01 and /tmp (the precheck checks this too).
  • No Data Guard switchover/failover in progress; in a Data Guard pair, patch the standby first.
  • No conflicting jobs or maintenance windows.
  • Read the RU's patch notes for known issues.
  • All DB system nodes are up.
  • Non-production first — test the RU on a test DB system before production.

Option A: The OCI Console

On the DB system page open Updates, pick the version, and choose Precheck and then Apply; do the same on the Database Home page. That's the simplest route and gives the same result as the commands below.

Option B: dbcli — Step by Step

Run these as root on the DB system host (mine is dbtest).

1Update the CLI

The tooling must be current before it can see new patches:

BASH
[root@dbtest ~]# cliadm update-dbcli
[root@dbtest ~]# dbcli list-jobs            # wait for "DcsCli patching" to show Success

The warning says cliadm update-dbcli will be deprecated — dbcli will be updated along with the DCS agent automatically.

2See Installed and Available Versions

BASH
[root@dbtest ~]# dbcli describe-component
[root@dbtest ~]# dbcli describe-latestpatch

GI and DB are at 19.23; 19.24 is available.

3Precheck the Server (GI) Patch

BASH
[root@dbtest ~]# dbcli update-server -v 19.24.0.0.0 --precheck
[root@dbtest ~]# dbcli describe-job -i <job_id>

4Apply the Server Patch

This patches Grid Infrastructure (rolling on a two-node RAC DB system):

BASH
[root@dbtest ~]# dbcli update-server -v 19.24.0.0.0
[root@dbtest ~]# dbcli describe-job -i <job_id>
[root@dbtest ~]# dbcli describe-component

The system version and GI are now 19.24; the database home is still 19.23.

5Patch the Database Home

Find the home's ID, precheck, then apply:

BASH
[root@dbtest ~]# dbcli list-dbhomes
[root@dbtest ~]# dbcli update-dbhome -i <dbhome_id> -v 19.24.0.0 --precheck
[root@dbtest ~]# dbcli describe-job -i <job_id>
[root@dbtest ~]# dbcli update-dbhome -i <dbhome_id> -v 19.24.0.0
[root@dbtest ~]# dbcli describe-job -i <job_id>
[root@dbtest ~]# dbcli list-dbhomes

The home OraDB19000_home1 is now at 19.24.

6Post-Patching Verification

update-dbhome runs datapatch for the databases in the home, but check it — a failed datapatch doesn't always fail the job:

BASH
$ $ORACLE_HOME/OPatch/opatch lspatches
SQL> select banner_full from v$version;
SQL> select patch_id, action, status, description
       from dba_registry_sqlpatch order by action_time;
$ lsnrctl status
$ srvctl status database -d <db_unique_name>
  • The binaries show the 19.24 RU, and dba_registry_sqlpatch has a SUCCESS row for it.
  • The listener and services are up, and applications reconnect.
