Why reverse-migrate with MI link?

Most MI link articles cover moving SQL Server into Azure SQL Managed Instance. The link also works the other way: with SQL Server 2025 and a managed instance on the SQL Server 2025 update policy, the managed instance can be the initial primary and SQL Server the secondary. After a planned failover, the database is read/write on SQL Server with near-zero downtime.

Typical reasons: moving back to IaaS for feature needs, cost, regulatory copies, or keeping an exit path from PaaS.

The one rule that matters: the managed instance must use the SQL Server 2025 update policy. Linking or failing over from MI to SQL Server 2025 is not supported with a mismatched policy, and moving an instance to a newer policy permanently upgrades its internal database format. Set it when you create the MI.

Architecture

Both servers sit in one VNet on separate subnets. The link is a distributed availability group between the MI and SQL Server, replicating over the database mirroring endpoint on TCP 5022 in both directions.

Prerequisites

  • Azure subscription with Contributor on the resource group.
  • An Entra ID work/school account for the SSMS Azure sign-in. Personal Microsoft accounts (outlook.com, outlook.in) are rejected – see issue 5.
  • sysadmin on the SQL Server VM and the MI admin login.
  • SSMS 21 or later on the VM (it contains the MI link wizards).
  • SQL Server 2025 patched to the latest cumulative update.
  • Azure CLI, or simply Azure Cloud Shell in the portal (the VM has no CLI by default – issue 3).

Step 1 – Networking

Run these in Azure Cloud Shell (Bash).

1.1 Resource group, VNet and VM subnet

az group create -n rg-milink-lab -l westus3
az network vnet create -g rg-milink-lab -n vnet-milink \
  --address-prefixes 10.50.0.0/16 \
  --subnet-name snet-sqlvm --subnet-prefixes 10.50.2.0/24

1.2 MI subnet (delegated, with NSG and route table)

az network nsg create -g rg-milink-lab -n nsg-sqlmi
az network route-table create -g rg-milink-lab -n rt-sqlmi
az network vnet subnet create -g rg-milink-lab --vnet-name vnet-milink \
  -n snet-sqlmi --address-prefixes 10.50.1.0/24 \
  --delegations Microsoft.Sql/managedInstances \
  --network-security-group nsg-sqlmi --route-table rt-sqlmi

1.3 VM subnet NSG

az network nsg create -g rg-milink-lab -n nsg-sqlvm
az network vnet subnet update -g rg-milink-lab --vnet-name vnet-milink \
  -n snet-sqlvm --network-security-group nsg-sqlvm

1.4 Link rules

NSGDirectionSourceDestinationDest. portPurpose
nsg-sqlmiInbound10.50.2.0/2410.50.1.0/245022VM → MI endpoint
nsg-sqlmiOutbound10.50.1.0/2410.50.2.0/245022MI → VM endpoint
nsg-sqlmiInbound10.50.2.0/2410.50.1.0/241433, 11000-11999SSMS/apps → MI (redirect)
nsg-sqlvmInbound10.50.1.0/2410.50.2.0/245022MI → VM endpoint
nsg-sqlvmInboundYour public IP10.50.2.0/243389RDP (or use Bastion)
Source port must be *. Only the destination port is fixed. The caller connects from a random high port, so a rule with source port 5022 never matches. This exact mistake broke my MI → VM connectivity (issue 2).
az network nsg rule create -g rg-milink-lab --nsg-name nsg-sqlmi -n allow-5022-in-from-vm \
  --priority 300 --direction Inbound --access Allow --protocol Tcp \
  --source-address-prefixes 10.50.2.0/24 --source-port-ranges '*' \
  --destination-address-prefixes 10.50.1.0/24 --destination-port-ranges 5022

az network nsg rule create -g rg-milink-lab --nsg-name nsg-sqlmi -n allow-5022-out-to-vm \
  --priority 300 --direction Outbound --access Allow --protocol Tcp \
  --source-address-prefixes 10.50.1.0/24 --source-port-ranges '*' \
  --destination-address-prefixes 10.50.2.0/24 --destination-port-ranges 5022

az network nsg rule create -g rg-milink-lab --nsg-name nsg-sqlmi -n allow-sql-in-from-vm \
  --priority 310 --direction Inbound --access Allow --protocol Tcp \
  --source-address-prefixes 10.50.2.0/24 --source-port-ranges '*' \
  --destination-address-prefixes 10.50.1.0/24 --destination-port-ranges 1433 11000-11999

az network nsg rule create -g rg-milink-lab --nsg-name nsg-sqlvm -n allow-5022-in-from-mi \
  --priority 300 --direction Inbound --access Allow --protocol Tcp \
  --source-address-prefixes 10.50.1.0/24 --source-port-ranges '*' \
  --destination-port-ranges 5022

az network nsg rule create -g rg-milink-lab --nsg-name nsg-sqlvm -n allow-rdp-myip \
  --priority 320 --direction Inbound --access Allow --protocol Tcp \
  --source-address-prefixes <your-public-ip>/32 --source-port-ranges '*' \
  --destination-port-ranges 3389

Leave the Microsoft.Sql-managedInstances_UseOnly_* rules that the MI deployment adds untouched. If the portal also attached an NSG to the VM's NIC, add the 5022 inbound rule there too.

Step 2 – Create the source Managed Instance

  1. Portal → Azure SQL → Create → SQL managed instances → Single instance.
  2. Basics: rg-milink-lab, name sqlmi-src-01, same region. General Purpose, 4 vCores, 64 GB. SQL authentication (e.g. miadmin).
  3. Networking: vnet-milink / snet-sqlmi, connection type Redirect, public endpoint disabled.
  4. Additional settings → Update policy → SQL Server 2025. Keep the default collation and match it on the VM.
  5. Review + create. Provisioning takes roughly 30 minutes to a few hours.

Once it's up, copy the host name (e.g. sqlmi-src-01.xxxx.database.windows.net), confirm the update policy on the Overview page, and create or restore your test database (NovaBank in my lab). MI databases are always in FULL recovery and backed up automatically, so no manual backup is needed when MI is the initial primary.

Step 3 – Handle TDE on the source database

MI encrypts every new database with TDE using a service-managed key. SQL Server can never access that Microsoft-held certificate, so the link wizard flags the database with Service-managed TDE protector and won't let you select it (issue 1).

Option A – Decrypt (used in this lab)

-- on the MI
ALTER DATABASE [NovaBank] SET ENCRYPTION OFF;

-- repeat until encryption_state = 1 (5 = decrypting)
SELECT DB_NAME(database_id) AS db, encryption_state, percent_complete
FROM sys.dm_database_encryption_keys
WHERE database_id = DB_ID('NovaBank');

-- then remove the key
USE [NovaBank];
DROP DATABASE ENCRYPTION KEY;

SELECT name, is_encrypted FROM sys.databases WHERE name = 'NovaBank';  -- 0

Wait 10–15 minutes for an automatic log backup to truncate log records written while TDE was on, then close and reopen the wizard. Its Refresh button didn't re-read the encryption state for me.

Option B – Customer-managed key (production-style)

Move the MI's TDE protector to a key in Azure Key Vault (grant the MI's managed identity Key Vault Crypto Service Encryption User). On the VM, install the SQL Server Connector for Azure Key Vault, enable the EKM provider, and open the same key with CREATE ASYMMETRIC KEY … FROM PROVIDER … CREATION_DISPOSITION = OPEN_EXISTING plus a login and credential mapped to it. The database stays encrypted end to end.

Step 4 – Create and prepare the SQL Server 2025 VM

4.1 Deploy

  1. Portal → Azure SQL → Create → SQL virtual machines → SQL Server 2025 Developer (or Enterprise) on Windows Server.
  2. Name vm-sql2025-tgt, size Standard_D4s_v5, VNet vnet-milink / snet-sqlvm.
  3. SQL connectivity Private, port 1433, SQL authentication on; separate data and log disks.
  4. After deployment, set the NIC private IP to Static (10.50.2.4).

4.2 Enable Always On availability groups

Install-Module SqlServer -Force -AllowClobber
Enable-SqlAlwaysOn -ServerInstance "localhost" -Force   # restarts SQL Server

4.3 Trace flags 1800 and 9567

1800 aligns log I/O with MI's 4 KB sector size; 9567 compresses automatic seeding. Apply now and persist as startup parameters (-T1800, -T9567 in SQL Server Configuration Manager).

DBCC TRACEON (1800, -1);
DBCC TRACEON (9567, -1);
DBCC TRACESTATUS (-1);
SELECT SERVERPROPERTY('IsHadrEnabled') AS hadr_enabled;   -- 1

4.4 Database master key (the validator fails without it)

USE master;
IF NOT EXISTS (SELECT 1 FROM sys.symmetric_keys WHERE name = '##MS_DatabaseMasterKey##')
  CREATE MASTER KEY ENCRYPTION BY PASSWORD = '<StrongPassword>';

4.5 Certificate and mirroring endpoint (if the wizard asks for them)

USE master;
CREATE CERTIFICATE MILinkCert
  WITH SUBJECT = 'MI link endpoint certificate', EXPIRY_DATE = '2030-12-31';
GO
CREATE ENDPOINT MILinkEndpoint
  STATE = STARTED
  AS TCP (LISTENER_PORT = 5022, LISTENER_IP = ALL)
  FOR DATABASE_MIRRORING (
      ROLE = ALL,
      AUTHENTICATION = CERTIFICATE MILinkCert,
      ENCRYPTION = REQUIRED ALGORITHM AES);

4.6 Windows Firewall

New-NetFirewallRule -DisplayName "SQL MI link 5022" -Direction Inbound -Protocol TCP -LocalPort 5022 -Action Allow -Profile Any
New-NetFirewallRule -DisplayName "SQL 1433" -Direction Inbound -Protocol TCP -LocalPort 1433 -Action Allow -Profile Any
Use -Profile Any: Azure VM networks often show up as the Public profile, so a Domain/Private-only rule never applies.

Step 5 – Test connectivity

From the VM:

$mi = "sqlmi-src-01.xxxx.database.windows.net"
Resolve-DnsName $mi
Test-NetConnection $mi -Port 1433
Test-NetConnection $mi -Port 5022

Then in SSMS, run the MI link Network Checker (right-click the MI database → Azure SQL Managed Instance link → Test connection). It creates helper Agent jobs on both sides and tests each direction. Use the VM's private IP as the SQL Server address – MI can't resolve a bare VM host name.

Goal: both SQL Server can reach SQL Managed Instance and SQL Managed Instance can reach SQL Server show green.

If a direction fails, Network Watcher's IP flow verify names the blocking NSG rule:

az network watcher test-ip-flow -g rg-milink-lab --vm vm-sql2025-tgt \
  --direction Inbound --protocol TCP \
  --local 10.50.2.4:5022 --remote <MI-private-IP>:12345

Step 6 – Create the MI link

  1. On the VM, open SSMS and connect to the MI (the initial primary) and to the local SQL Server.
  2. Under the MI, right-click NovaBank → Azure SQL Managed Instance link → New…
  3. Specify Link Options / Requirements: fix anything flagged.
  4. Select Databases: NovaBank. It must not show the TDE warning (Step 3).
  5. Specify Secondary Replica → Add secondary replica → connect to the SQL Server VM.
  6. Login to Azure: sign in with your Entra ID work account.
  7. Validation: everything green; trace-flag rows may stay yellow if you skip them.
  8. Summary → optionally Script to save the generated T-SQL/PowerShell → Finish.

The wizard builds the availability group and distributed AG, exchanges certificates and starts automatic seeding. When done, NovaBank appears on the VM as a read-only, synchronized secondary.

-- on MI
INSERT NovaBank.dbo.Orders (Customer, Amount) VALUES ('LinkTest', 1);
-- on VM (read-only secondary)
SELECT TOP 5 * FROM NovaBank.dbo.Orders ORDER BY OrderId DESC;

Step 7 – Monitor and fail over to the VM

Monitor

SELECT DB_NAME(database_id) AS db, is_primary_replica,
       synchronization_state_desc, synchronization_health_desc,
       last_hardened_lsn, last_commit_time
FROM sys.dm_hadr_database_replica_states;

Cutover

  1. Stop the application / writes on the MI.
  2. Confirm both replicas report the same last_hardened_lsn and SYNCHRONIZED; compare row counts.
  3. SSMS (connected to MI) → NovaBank → Azure SQL Managed Instance link → Failover…
  4. Sign in to Azure with the Entra ID account, choose Planned failover.
  5. Tick Remove link after successful failover for a one-way migration, or keep the link to be able to fail back to MI.
  6. Verify on the VM and repoint the application.
SELECT name, state_desc, is_read_only, recovery_model_desc
FROM sys.databases WHERE name = 'NovaBank';   -- ONLINE, is_read_only = 0

Step 8 – Post-migration tasks

  • Recreate logins (match SIDs for SQL logins), Agent jobs, linked servers and credentials – the link only moves the database.
  • Fix orphaned users: ALTER USER [x] WITH LOGIN = [x];
  • Configure backups on the VM and take a full backup immediately.
  • Optionally re-enable TDE on the VM with a local certificate (back up the certificate!).
  • Update statistics; consider COMPATIBILITY_LEVEL = 170.
  • Remove the link (if kept) and stop/delete the MI when no longer needed.

Issues I hit and how I fixed them

These came up in order during the lab. Each one blocked progress until fixed.

1. "Service-managed TDE protector" in Select Databases

SymptomNovaBank (2872 MB) showed a warning icon and couldn't be selected. Decrypting alone didn't clear it.

CauseMI's default TDE uses a Microsoft-managed certificate that SQL Server can't obtain; the database encryption key was still present after decryption.

FixSET ENCRYPTION OFF → wait for encryption_state = 1 → DROP DATABASE ENCRYPTION KEY → wait for a log backup → close and reopen the wizard.

2. Network Checker: "SQL Managed Instance cannot reach SQL Server"

SymptomSQL Server → MI on ports 5022 and 11002 succeeded; MI → SQL Server failed.

CauseThe inbound rule on the VM NSG had SourcePortRanges = 5022. The MI connects from an ephemeral port, so the rule never matched and DenyAllInbound dropped the traffic. The MI-side NSG was fine.

Fix

az network nsg rule update -g rg-milink-lab --nsg-name nsg-sqlvm -n mi-vm-endpoint --source-port-ranges '*'
az network nsg rule update -g rg-milink-lab --nsg-name nsg-sqlvm -n vm-mi --source-port-ranges '*'

3. "az is not recognized" on the VM

SymptomRunning az network nsg rule list in PowerShell on the VM failed.

CauseAzure CLI isn't installed on marketplace SQL VMs.

FixUse Azure Cloud Shell in the portal, or install it: winget install -e --id Microsoft.AzureCLI, reopen PowerShell, az login.

4. Validation: "Database master key is not present on the SQL Server"

SymptomFirst validation row red; certificate and endpoint checks skipped; trace flag 1800 and 9567 warnings.

CauseNo database master key in master on the VM, so the endpoint certificate couldn't be created; trace flags not set.

FixCREATE MASTER KEY in master, DBCC TRACEON (1800, -1) and (9567, -1), then Re-run validation. Create the certificate and endpoint (Step 4.5) if those rows turn red.

5. Failover sign-in: AADSTS500200

Symptom"User account '…@outlook.in' is a personal Microsoft account. Personal Microsoft accounts are not supported for this application."

CauseThe SSMS Azure sign-in only accepts Entra ID work/school accounts.

FixEntra ID → Users → New user (sqladmin@<tenant>.onmicrosoft.com) → assign Contributor on rg-milink-lab → sign in once in a private browser window to set the password → in the wizard choose Use another account. Remove the personal account from SSMS's Azure account settings if it keeps being picked.

Cleanup and references

az group delete -n rg-milink-lab --yes --no-wait
