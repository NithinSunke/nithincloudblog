LUN Migration: Adding New LUNs to Oracle ASM

By Sunke Nithin · June 26, 2019   LinuxStorage

When storage is replaced or grows, new SAN LUNs have to be brought into Oracle ASM on every RAC node. This is the action plan I followed on a two-node cluster (dbdvl01, dbdvl02) with ASMLib: check the environment, label the new LUNs, check ASM sees them, add them to a disk group (or create a new one), and watch the rebalance. Part 2 uses the new disk group to move the OCR and voting disks.

Action Plan

  1. Collect the details from the environment
  2. Verify the LUN details
  3. Create the ASM disks
  4. Verify ASM can see them
  5. Add them to a disk group
  6. Monitor the rebalance
  7. Verify from both ASM instances

1Collect the Details from the Environment

Record the cluster resources and the current disks and disk groups before changing anything:

BASH
[grid@dbdvl01 ~]$ crsctl stat res -t
[grid@dbdvl01 ~]$ sqlplus / as sysasm

SQL> select group_number, name, state, type, total_mb, free_mb from v$asm_diskgroup;
SQL> select group_number, name, path, header_status, mount_status, state from v$asm_disk;
SQL> select * from v$asm_operation;

2Verify the LUN Details

The new LUN must be visible — with the same multipath name — on every node:

BASH
[root@dbdvl01 ~]# multipath -ll          # the new LUN is visible on BOTH nodes
[root@dbdvl01 ~]# fdisk -l /dev/mapper/vpath3
[root@dbdvl01 ~]# oracleasm listdisks

3Create the ASM Disks

Label the LUNs with ASMLib on one node, then scan on the others:

BASH
# node 1 (OL6: /etc/init.d/oracleasm; OL7+: /usr/sbin/oracleasm)
[root@dbdvl01 ~]# oracleasm createdisk OCRVD1 /dev/mapper/vpath3p1
[root@dbdvl01 ~]# oracleasm createdisk OCRVD2 /dev/mapper/vpath4p1
[root@dbdvl01 ~]# oracleasm createdisk OCRVD3 /dev/mapper/vpath5p1
[root@dbdvl01 ~]# oracleasm listdisks

# node 2: pick up the new labels
[root@dbdvl02 ~]# oracleasm scandisks
[root@dbdvl02 ~]# oracleasm listdisks
Use a partition on the multipath device (vpath3p1), or the whole device — but always the multipath name, never an individual /dev/sdX path. On systems without ASMLib, use udev rules or ASM Filter Driver instead.

4Verify ASM Can See the New Disks

SQL
SQL> select path, header_status, mount_status, state from v$asm_disk
      where header_status in ('PROVISIONED','CANDIDATE');

A disk labelled by ASMLib shows HEADER_STATUS = PROVISIONED (a raw candidate disk shows CANDIDATE). Run this on both nodes.

5Add the Disks to a Disk Group

To grow or migrate an existing disk group, add the new disk; ASM rebalances the data onto it:

SQL
SQL> alter diskgroup DATA add disk 'ORCL:DATA2' rebalance power 4;

To move to new LUNs completely, add all the new disks and drop the old ones in the same command — one rebalance moves everything, and the old disks can be removed from the server once it finishes:

SQL
SQL> alter diskgroup DATA
       add  disk 'ORCL:DATA2', 'ORCL:DATA3'
       drop disk DATA_0000, DATA_0001
       rebalance power 4;

For a new disk group — like the one for OCR and voting disks in Part 2:

SQL
SQL> create diskgroup OCR normal redundancy
       disk 'ORCL:OCRVD1', 'ORCL:OCRVD2', 'ORCL:OCRVD3'
       attribute 'compatible.asm' = '19.0.0.0';   -- at least 11.2 for voting files

-- mount it on the other node(s) too
[grid@dbdvl02 ~]$ srvctl start diskgroup -diskgroup OCR -node dbdvl02
Correction: my original notes used create diskgroup NEW_OCRVD add disk 'ORCL:OCRVD2', which isn't valid syntax (add disk belongs to alter diskgroup) and mixed up the disk names (it labelled DATA2 and then added OCRVD2). The commands above are consistent.

6Monitor the Rebalance

SQL
SQL> select group_number, operation, state, power, est_minutes from v$asm_operation;
-- no rows = rebalance finished

7Verify from Both ASM Instances

SQL
SQL> select group_number, name, path, header_status, mount_status, state from v$asm_disk;
SQL> select group_number, name, total_mb, free_mb from v$asm_disk_stat;

All new disks should be MEMBER / CACHED / NORMAL on both nodes, with the expected sizes.
