IAM in OCI: The Building Blocks

By Sunke Nithin · December 16, 2019   CLOUDOCI

Identity and Access Management (IAM) in Oracle Cloud Infrastructure decides who can do what with which resources. These are the concepts you meet first — and that every OCI certification asks about.

ConceptIn short
ResourceAnything you create in OCI: instances, block volumes, VCNs, subnets, buckets, databases…
UserA person or system that works with OCI resources. The end users of your applications are usually not IAM users
GroupA set of users who need the same access. Permissions are given to groups, never directly to users
Dynamic groupA group of resources (e.g. all instances in a compartment) defined by matching rules, so they can call OCI APIs without user credentials
CompartmentA logical container that organises and isolates resources — for access control, cost tracking and quotas. Compartments can be nested
TenancyYour account: the root compartment containing everything. Oracle creates it when you sign up
PolicyStatements that allow a group to act on resources in a compartment or the whole tenancy
Home regionThe region where IAM changes are made; they replicate to all subscribed regions
Identity domainThe user and group store for the tenancy (the evolution of Oracle Identity Cloud Service). It can federate with an external identity provider such as Microsoft Entra ID or Okta

Compartments

A common design is one compartment per environment or business area — Network, Prod, Dev, Security — with sub-compartments as needed. A resource belongs to exactly one compartment but can be moved. Access granted on a compartment is inherited by its sub-compartments, and access granted on the tenancy applies everywhere.

Policies

Policies are written in readable statements: Allow group <group> to <verb> <resource-type> in <compartment | tenancy>.

POLICY
Allow group NetworkAdmins to manage virtual-network-family in compartment Network
Allow group DBAdmins to manage database-family in compartment Prod:Databases
Allow group Developers to use instances in compartment Dev
Allow group Auditors to inspect all-resources in tenancy
VerbAllows
inspectList resources
readInspect, plus see details and metadata
useRead, plus work with existing resources (e.g. start/stop an instance)
manageEverything, including create and delete

A policy attached to a compartment can only grant access to that compartment and its children — attach policies as low in the tree as they need to be.

Federation

With federation, users and group membership live in your corporate identity provider, and OCI maps those groups to OCI groups. Authorisation is still done by OCI policies. New tenancies use identity domains, which can federate through SAML or SCIM provisioning.

The Administrators Group

When the tenancy is created, the first user is placed in the Administrators group, and a built-in tenancy policy gives that group full access to everything. The group can't be deleted and must always have at least one member, and the policy can't be changed. Anyone added to Administrators gets full control — so add as few people as possible, and give everyone else narrower groups and policies.
