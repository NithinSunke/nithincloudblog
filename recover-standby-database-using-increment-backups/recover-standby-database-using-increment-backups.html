Recover a Standby Database Using Incremental Backups

By Sunke Nithin · June 20, 2019   DatabaseOracleDataguard

When a physical standby falls far behind — archived logs lost or deleted on the primary before they were shipped — you don't have to rebuild it. An incremental backup from the standby's SCN on the primary carries every changed block, and applying it to the standby rolls it forward in one step. Example: primary SUNKDEV on oradbdvl01, standby on orclstdy01, 11.2.0.4.

standby SCN→stop MRP→incremental from SCN (primary)→standby control file→copy→restore control file→catalog→recover→start MRP

The Gap

The primary is on log sequence 42, but the standby has only received and applied up to 35:

SQL · PRIMARY
SQL> archive log list
Database log mode              Archive Mode
Automatic archival             Enabled
Oldest online log sequence     40
Next log sequence to archive   42
Current log sequence           42
SQL · STANDBY
   THREAD# Last Sequence Received Last Sequence Applied Difference
---------- ---------------------- --------------------- ----------
         1                     35                    35          1

1Find the SCN to Start From

On the standby, use the lowest SCN among its data file headers (and compare with the database's current SCN — take the smaller):

SQL · STANDBY
select min(checkpoint_change#) from v$datafile_header where file# <> 0;
select current_scn from v$database;

Here the standby's SCN was 1114207 (the primary was at 1114514).

The current SCN alone can be higher than an individual data file's checkpoint, which would leave that file behind. The minimum data file header SCN is the safe starting point.

2Stop Redo Apply and Shut Down the Standby

SQL · STANDBY
alter database recover managed standby database cancel;
shutdown immediate

3Incremental Backup from the SCN on the Primary

RMAN · PRIMARY
run {
  allocate channel c1 type disk format '/c01/standby/%U.bkp';
  backup incremental from scn 1114207 database;
}
OUTPUT

4Back Up a Standby Control File on the Primary

RMAN · PRIMARY
BACKUP CURRENT CONTROLFILE FOR STANDBY FORMAT '/c01/standby/stdby_ctl_%U' TAG 'FORSTDBY';
OUTPUT
including standby control file in backup set
piece handle=/c01/standby/stdby_ctl_15u4jc1m_1_1 tag=FORSTDBY

A fresh standby control file brings over structural changes made on the primary (new data files, for example) and the current SCN.

5Copy the Backup Pieces to the Standby

BASH · PRIMARY
scp -p /c01/standby/* oracle@orclstdy01:/c01/standby/

6Restore the Standby Control File

SQL · STANDBY
startup nomount
RMAN · STANDBY
RMAN> restore standby controlfile from '/c01/standby/stdby_ctl_15u4jc1m_1_1';
OUTPUT
output file name=/b01/oradata/sunkdev/control01.ctl
output file name=/c01/fra/sunkdev/control02.ctl
Finished restore at 20-JUN-19
SQL · STANDBY
alter database mount standby database;
If the standby's data file paths differ from the primary's, the new control file has the primary paths. Catalog the standby's own data files (catalog start with '/standby/datafile/path/';) and run switch database to copy; before recovering.

7Catalog the Incremental Backup

RMAN · STANDBY
RMAN> catalog start with '/c01/standby';

RMAN also catalogs the archived logs it finds in the standby's recovery area, then lists the three backup pieces and asks to confirm — answer yes.

8Recover the Standby

RMAN · STANDBY
RMAN> recover database noredo;

NOREDO applies just the incremental backup. I ran a plain recover database, which applies the incremental and then tries to continue with archived logs:

9Restart Redo Apply

SQL · STANDBY
alter database recover managed standby database disconnect from session;

If standby redo logs are configured, clear them so they match the new control file: alter database clear logfile group <n>; for each standby log group (with MRP stopped).

10Verify

Switch a log on the primary (alter system switch logfile;) and check the standby is receiving and applying again:

SQL · STANDBY
select rec.thread#, rec.last_rec "Last Sequence Received",
       app.last_app "Last Sequence Applied",
       (rec.last_rec - app.last_app) "Difference"
  from (select thread#, max(sequence#) last_rec from v$archived_log
         where resetlogs_id = (select max(resetlogs_id) from v$archived_log)
         group by thread#) rec,
       (select thread#, max(sequence#) last_app from v$archived_log
         where resetlogs_id = (select max(resetlogs_id) from v$archived_log)
           and applied = 'YES' and registrar = 'RFS'
         group by thread#) app
 where rec.thread# = app.thread# and rec.thread# != 0
 order by rec.thread#;
OUTPUT
   THREAD# Last Sequence Received Last Sequence Applied Difference
---------- ---------------------- --------------------- ----------
         1                     45                    45          0

The gap is closed — received and applied are both at 45.

On 18c and Later: One Command

Newer versions automate all of this. On the standby, with MRP stopped:

RMAN · STANDBY
RMAN> recover standby database from service primary_tns;

RMAN fetches the incremental over the network from the primary, refreshes the standby control file and data file names, and rolls the standby forward. On 12c, recover database from service primary_tns noredo using compressed backupset; does the incremental part.
