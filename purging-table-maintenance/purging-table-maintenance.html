Purging Old Data from a Large Table with Partitioning

By Sunke Nithin · June 4, 2024   DatabaseOracle

A customer's cust_data table holds about 29 million rows from March 2009 to February 2018. Company policy says data older than five years — before February 2013 — must go. Deleting tens of millions of rows is slow, generates huge amounts of undo and redo, and leaves the table fragmented. The better way: partition the table by month online, then drop the old partitions, which takes seconds.

back up→interim partitioned table→DBMS_REDEFINITION (online)→drop old partitions→stats & checks

Set Up the Demo Table

SQL
CREATE TABLE cust_data (
  customer_id    NUMBER,
  customer_name  VARCHAR2(100),
  phone_number   VARCHAR2(20),
  cust_date      DATE
);

Load it with test data spread randomly between March 2009 and February 2018:

SQL
CREATE OR REPLACE PROCEDURE insert_cust_data (p_rows IN NUMBER DEFAULT 30000000) AS
  v_batch_size NUMBER := 1000;                         -- commit every 1000 rows
  v_start_date DATE   := DATE '2009-03-01';
  v_end_date   DATE   := DATE '2018-02-28';
BEGIN
  FOR i IN 1 .. CEIL(p_rows / v_batch_size) LOOP
    FOR j IN 1 .. v_batch_size LOOP
      INSERT INTO cust_data (customer_id, customer_name, phone_number, cust_date)
      VALUES (
        (i - 1) * v_batch_size + j,
        'Customer_' || ((i - 1) * v_batch_size + j),
        '123-456-' || LPAD(TRUNC(DBMS_RANDOM.VALUE(0, 9999)), 4, '0'),
        v_start_date + TRUNC(DBMS_RANDOM.VALUE(0, v_end_date - v_start_date))
      );
    END LOOP;
    COMMIT;
  END LOOP;
END;
/
SQL
EXECUTE insert_cust_data(29380000);
My original version looped to 100 million rows, while the scenario talks about 20 million; my test table ended up with 29,380,000. The procedure now takes the row count as a parameter.
SQL
CREATE UNIQUE INDEX nsunke.cust_indx ON nsunke.cust_data (customer_id) PARALLEL;
ALTER INDEX nsunke.cust_indx NOPARALLEL;
ALTER TABLE nsunke.cust_data ADD CONSTRAINT cust_id_pk PRIMARY KEY (customer_id);

Online redefinition uses the primary key by default to track changes during the copy. (A table without one can be redefined with options_flag => DBMS_REDEFINITION.cons_use_rowid.)

  FROM cust_data

2Create the Interim Partitioned Table

Same columns, partitioned by month on cust_date. Interval partitioning creates a partition for each month automatically as rows arrive, so there's no list of 100+ partitions to script:

SQL
CREATE TABLE cust_data_part (
  customer_id    NUMBER,
  customer_name  VARCHAR2(100),
  phone_number   VARCHAR2(20),
  cust_date      DATE
)
PARTITION BY RANGE (cust_date)
INTERVAL (NUMTOYMINTERVAL(1, 'MONTH'))
(
  PARTITION p_before_2009_03 VALUES LESS THAN (DATE '2009-03-01')
);

p_before_2009_03 stays empty (the data starts in March 2009). It's there because an interval-partitioned table needs one range partition to anchor the intervals — and that one can't be dropped, which is why it shouldn't hold any data.

Why not hand-made monthly partitions?

My first version created PART_MAR_2009 VALUES LESS THAN ('01-MAR-2009') and so on, then added the rest in a loop starting in May. Two problems: a partition named for a month held the previous month's data (the bound is exclusive), and the loop's first partition covered both April and May, so they couldn't be dropped separately. Interval partitioning avoids both — and with DROP PARTITION FOR (date) you never need to know the generated names.

3Check the Table Can Be Redefined

SQL
EXEC DBMS_REDEFINITION.can_redef_table('NSUNKE', 'CUST_DATA');

No error means it can. For a large table, use more parallelism for the copy — if the database is in the cloud, this is a good moment to scale up CPUs temporarily:

SQL
ALTER SESSION FORCE PARALLEL DML PARALLEL 4;
ALTER SESSION FORCE PARALLEL QUERY PARALLEL 4;

4Redefine the Table Online

SQL
SET SERVEROUTPUT ON
DECLARE
  l_num_errors PLS_INTEGER;
BEGIN
  DBMS_REDEFINITION.start_redef_table('NSUNKE', 'CUST_DATA', 'CUST_DATA_PART');

  DBMS_REDEFINITION.copy_table_dependents(
    uname            => 'NSUNKE',
    orig_table       => 'CUST_DATA',
    int_table        => 'CUST_DATA_PART',
    copy_indexes     => DBMS_REDEFINITION.cons_orig_params,
    copy_triggers    => TRUE,
    copy_constraints => TRUE,
    copy_privileges  => TRUE,
    ignore_errors    => FALSE,
    num_errors       => l_num_errors,
    copy_statistics  => FALSE,
    copy_mvlog       => FALSE);

  DBMS_REDEFINITION.sync_interim_table('NSUNKE', 'CUST_DATA', 'CUST_DATA_PART');
  DBMS_REDEFINITION.finish_redef_table('NSUNKE', 'CUST_DATA', 'CUST_DATA_PART');
EXCEPTION
  WHEN OTHERS THEN
    DBMS_OUTPUT.put_line('Error: ' || SQLERRM);
    DBMS_REDEFINITION.abort_redef_table('NSUNKE', 'CUST_DATA', 'CUST_DATA_PART');
    RAISE;
END;
/
  • start_redef_table copies all rows into the interim table — into the right monthly partitions — while the original stays fully usable.
  • copy_table_dependents recreates the indexes, constraints, triggers and grants on the interim table.
  • sync_interim_table applies changes made during the copy.
  • finish_redef_table swaps the two tables in a brief lock. CUST_DATA is now partitioned, and CUST_DATA_PART holds the old, non-partitioned copy.

Compare row counts, then drop the old copy:

SQL
SQL> select count(*) from nsunke.cust_data_part;
  COUNT(*)
----------
  29380000

SQL> select count(*) from nsunke.cust_data;
  COUNT(*)
----------
  29380000

SQL> drop table nsunke.cust_data_part purge;

5Purge: Drop the Old Partitions

This is the step that actually removes the data — each month older than February 2013 disappears as a quick dictionary operation, with no undo for millions of rows:

SQL
-- Drop every monthly partition holding data before February 2013
DECLARE
  v_month DATE := DATE '2009-03-01';
BEGIN
  WHILE v_month < DATE '2013-02-01' LOOP
    EXECUTE IMMEDIATE
      'ALTER TABLE nsunke.cust_data DROP PARTITION FOR (DATE ''' ||
      TO_CHAR(v_month, 'YYYY-MM-DD') || ''') UPDATE GLOBAL INDEXES';
    v_month := ADD_MONTHS(v_month, 1);
  END LOOP;
END;
/

UPDATE GLOBAL INDEXES keeps the primary key index usable, so the table stays online throughout. Check what's left:

SQL
SELECT MIN(cust_date), MAX(cust_date), COUNT(*) FROM nsunke.cust_data;

SELECT partition_name, high_value
  FROM dba_tab_partitions
 WHERE table_owner = 'NSUNKE' AND table_name = 'CUST_DATA'
 ORDER BY partition_position;

From now on, the monthly purge is a single DROP PARTITION FOR each month.

6Gather Statistics and Check Indexes

EXEC DBMS_STATS.gather_table_stats(ownname => 'NSUNKE', tabname => 'CUST_DATA', cascade => TRUE, degree => 4);
SQL
SELECT index_name, status FROM dba_indexes WHERE owner = 'NSUNKE' AND status = 'UNUSABLE';
SELECT index_name, partition_name, status FROM dba_ind_partitions WHERE index_owner = 'NSUNKE' AND status = 'UNUSABLE';

If anything shows as UNUSABLE, rebuild it: ALTER INDEX nsunke.cust_indx REBUILD ONLINE;

On 12.2 and Later: One Statement

Since 12.2 you can convert a non-partitioned table to a partitioned one online with a single ALTER TABLE — no interim table or DBMS_REDEFINITION:

SQL
ALTER TABLE nsunke.cust_data
  MODIFY PARTITION BY RANGE (cust_date)
  INTERVAL (NUMTOYMINTERVAL(1, 'MONTH'))
  ( PARTITION p_before_2009_03 VALUES LESS THAN (DATE '2009-03-01') )
  ONLINE
  UPDATE INDEXES;

DBMS_REDEFINITION is still useful when you need to change more than the partitioning at the same time, such as columns, storage or tablespace.
