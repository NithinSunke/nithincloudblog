Oracle Grid and Database 19c Home Out-of-Place Patching

By Sunke Nithin · June 11, 2024   DatabaseOraclePatching

Out-of-place patching with opatchauto -outofplace clones the Grid and database homes, patches the clones, and moves the stack over to them — the original homes are left untouched. Besides being an easy rollback, it's handy when the file system holding the current homes is full: you can put the clones somewhere with more space.

Supported from Oracle Database Enterprise Edition 12.2.0.1 onwards. My environment is Oracle Restart (single-instance HA, "SIHA") on host ol7asmdb01 with a 19c database crac1d, patched to the 19.23 RU (GI patch 36233126).

Assumptions

  1. Oracle Restart is configured with a 19c Grid home and a 19c database home.
  2. The latest RU and OPatch are downloaded from My Oracle Support, and OPatch is updated in both homes.
  3. There's enough free space for a second copy of each home (about 15 GB for Grid, 10 GB for the database).

1Run opatchauto as root

One command patches both homes. It asks for a clone path for each — press Enter for the default (…_2 next to the original) or type a path on another mount point if the current one is short of space:

[root@ol7asmdb01 patch]# $ORACLE_HOME/OPatch/opatchauto apply /u01/patch/36233126 -outofplace

2What Happened

PhaseWhat opatchauto did
PrechecksVerified the patches apply to both homes and ran SQL-patch applicability checks
CloneCopied /u01/app/19.0.0/grid → grid_2 and dbhome_1 → dbhome_2 while everything kept running
PatchApplied the binary patches to the clones, ran rootadd_rdbms.sh
SwitchStopped the stack, started CRS from grid_2, and modified the database to run from dbhome_2 — the only downtime
SQL patchRan datapatch in the database

Note that three of the sub-patches were skipped on the database home — they're Grid-only (OCW, ACFS, …), which is expected.

3Check datapatch Really Worked

Look closely at the output: the datapatch command failed, and the very next line says "SQL patch applied successfully". Don't trust the summary — check the registry, and if the 19.23 entry isn't SUCCESS, rerun datapatch from the new home:

BASH
$ export ORACLE_HOME=/u01/app/oracle/product/19.0.0/dbhome_2
$ export ORACLE_SID=crac1d
$ $ORACLE_HOME/OPatch/datapatch -verbose

SQL> select patch_id, action, status, description
       from dba_registry_sqlpatch order by action_time;

4Verify the Stack Runs from the New Homes

opatchauto itself warns: "verify the database is running from the desired Oracle home". Check, and fix with srvctl modify database -db crac1d -oraclehome … if needed:

BASH
$ srvctl config database -db crac1d | grep -i home
$ srvctl status database -db crac1d
$ crsctl stat res -t
$ /u01/app/19.0.0/grid_2/OPatch/opatch lspatches -oh /u01/app/19.0.0/grid_2
$ /u01/app/oracle/product/19.0.0/dbhome_2/OPatch/opatch lspatches

Then update /etc/oratab and the oracle / grid user profiles so ORACLE_HOME points to dbhome_2 and grid_2.

Timing: the whole session took about 215 minutes in my small lab VM — most of it copying and cloning, while the database was still up. The actual outage was only the stack restart near the end. Keep the old homes until you're sure you won't roll back, then remove them with deinstall.
