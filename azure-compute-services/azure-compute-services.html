Azure Compute Services: Virtual Machines, Scale Sets, App Service, Functions and Containers

Azure gives you at least seven ways to run code. They differ in one main way: how much of the stack you manage yourself and how much Azure manages for you. This post explains each service, shows when to pick it, and gives you a lab for each one that you can run from Cloud Shell.

1. The compute spectrum

Every compute service runs your code on servers in an Azure datacenter. What changes is who looks after what. With a virtual machine you patch the operating system, install the runtime and plan for scaling. With Azure Functions you upload a function and Azure does the rest. The services in between trade some control for less work.

Three cloud service models map onto this picture:

  • IaaS (Infrastructure as a Service): Virtual Machines and Scale Sets. You get a server; everything from the OS up is yours.
  • PaaS (Platform as a Service): App Service, Container Apps, and AKS for the cluster control plane. You bring code or a container; Azure runs the platform.
  • Serverless: Functions and Container Apps on the Consumption plan. No servers to size; you pay when code runs, and it can scale to zero.

2. Lab setup (do this once)

All labs run in Azure Cloud Shell (Bash), which already has the Azure CLI signed in. Open it from the >_ icon at the top of the portal. Each lab also lists the portal path if you'd rather click through.

# Variables used by every lab. Change LOCATION to a region near you if you like.
RG=compute-lab-rg
LOCATION=westus3
SUFFIX=$RANDOM            # makes global names unique

az group create --name $RG --location $LOCATION --tags env=lab topic=compute

Cost on a free account. The Azure free account includes 750 hours a month of B1s, B2pts v2 and B2ats v2 VMs for 12 months, App Service Free tier apps, 1 million Functions requests, and a monthly Container Apps grant of 180,000 vCPU-seconds, 360,000 GiB-seconds and 2 million requests. Load balancers, public IPs, extra VMs in a scale set and AKS nodes are billed against your credit. Every lab ends with a cleanup step, and section 10 removes everything in one command.

If a command says az doesn't know a containerapp command or a resource provider isn't registered, that's covered in the lab where it comes up.

Part 1 · IaaS

3. Azure Virtual Machines

An Azure Virtual Machine is a server running on Azure's hypervisor. You choose the operating system (Windows or Linux), the size (vCPUs and memory) and the disks, and you get full administrator access. It's the right choice when you need total control: lift-and-shift of an existing server, software that must be installed on the OS, an Oracle or SQL Server database you run yourself, or a custom network appliance.

A VM is never a single resource. When you create one, Azure creates several resources that work together:

Key concepts

ConceptWhat to know
Size familiesB burstable (cheap, dev/test), D general purpose, E memory optimized (databases), F compute optimized, L storage optimized, M very large memory, N GPU. A name like Standard_D4s_v5 means family D, 4 vCPUs, premium storage capable (s), version 5.
ImagesMarketplace images (Ubuntu, RHEL, Oracle Linux, Windows Server, SQL Server on Windows) or your own custom image from an Azure Compute Gallery.
Managed disksStandard HDD, Standard SSD, Premium SSD, Premium SSD v2 and Ultra Disk, in rising order of performance and price. Every VM has an OS disk; data disks are optional. Some sizes also have a temporary disk that is wiped when the VM moves.
AvailabilityAvailability sets spread VMs across fault and update domains in one datacenter. Availability zones spread them across physically separate datacenters in a region, which protects against a whole datacenter failing.
Stopped vs deallocatedShutting down from inside the OS leaves the VM Stopped and you still pay for compute. Stop in the portal (or az vm deallocate) makes it Stopped (deallocated): compute billing stops, and you only pay for disks and any static public IP.
ExtensionsSmall agents that run inside the VM after deployment, such as Custom Script, monitoring agents or Microsoft Entra login.

Coming from OCI? An Azure VM is like an OCI Compute instance, a VM size is a shape, a managed disk is a block volume, and an NSG works like an OCI network security group (Azure has no separate security list).

Lab 1: Create a Linux VM and serve a web page

Goal: create an Ubuntu VM on the free B1s size, install nginx, open port 80, then deallocate it so it stops costing compute hours. Time: about 15 minutes.

Portal path: Virtual machines → + Create → Azure virtual machine → choose compute-lab-rg, image Ubuntu Server 24.04 LTS, size Standard_B1s, authentication SSH public key, inbound ports HTTP (80), SSH (22) → Review + create.

CLI:

# 1. Create the VM (also creates the VNet, subnet, NSG, NIC, public IP and OS disk)
az vm create \
  --resource-group $RG --name lab-vm \
  --image Ubuntu2404 --size Standard_B1s \
  --admin-username azureuser --generate-ssh-keys \
  --public-ip-sku Standard

# 2. See everything that was created
az resource list -g $RG -o table

# 3. Install nginx without logging in, using Run Command
az vm run-command invoke -g $RG -n lab-vm \
  --command-id RunShellScript \
  --scripts "sudo apt-get update -y && sudo apt-get install -y nginx && echo '<h1>Hello from lab-vm</h1>' | sudo tee /var/www/html/index.html"

# 4. Open port 80 on the VM's NSG
az vm open-port -g $RG -n lab-vm --port 80

# 5. Get the public IP and test
VMIP=$(az vm show -d -g $RG -n lab-vm --query publicIps -o tsv)
curl http://$VMIP

# 6. Optional: SSH in
ssh azureuser@$VMIP

curl returns <h1>Hello from lab-vm</h1>, and the same page opens in your browser at the public IP.

# 7. Compare the two kinds of "stopped"
az vm deallocate -g $RG -n lab-vm
az vm get-instance-view -g $RG -n lab-vm \
  --query "instanceView.statuses[1].displayStatus" -o tsv   # VM deallocated

# Start it again later with: az vm start -g $RG -n lab-vm

Try next: attach a data disk with az vm disk attach -g $RG --vm-name lab-vm --name lab-data --new --size-gb 8, then SSH in and run lsblk to see it.

4. Virtual Machine Scale Sets

A Virtual Machine Scale Set (VMSS) manages a group of VMs as one unit. Instead of building ten web servers by hand, you describe one (image, size, startup script) and tell the scale set how many to run. It can then add or remove VMs automatically based on load or a schedule, spread them across availability zones, and sit behind a load balancer so users see one address.

Key concepts

  • Orchestration mode. Flexible lets you mix VM sizes and manage instances like normal VMs; it's the recommended mode for new workloads and the default when you create a scale set with the CLI or PowerShell. Uniform uses identical instances and is the older mode.
  • Scaling. Manual (set a count), metric-based autoscale (CPU, memory, queue length) or schedule-based (for example, 6 VMs during office hours and 2 at night).
  • Upgrade policy. Decides how instances pick up a model change: Automatic, Rolling (in batches) or Manual.
  • Stateless design. Any instance can be removed at any time, so keep session data and files outside the VM, for example in Azure Storage or a database.
  • The scale set itself is free; you pay for the VMs, disks and networking it creates.

Lab 2: Build an autoscaling web tier

Goal: create a two-instance scale set behind a load balancer, see traffic alternate between instances, add an autoscale rule and push CPU to trigger it. Time: about 25 minutes.

First, a cloud-init file that installs nginx and writes each instance's hostname into the page, so you can see which VM answered:

cat > cloud-init.txt <<'EOF'
#cloud-config
package_upgrade: false
packages:
  - nginx
runcmd:
  - echo "<h1>Served by $(hostname)</h1>" > /var/www/html/index.html
EOF
# 1. Create the scale set with 2 instances and a Standard load balancer
az vmss create \
  --resource-group $RG --name lab-vmss \
  --orchestration-mode Flexible \
  --image Ubuntu2404 --vm-sku Standard_B1s \
  --instance-count 2 \
  --upgrade-policy-mode Automatic \
  --admin-username azureuser --generate-ssh-keys \
  --custom-data cloud-init.txt \
  --lb-sku Standard

# 2. Add a load-balancing rule for port 80
az network lb rule create -g $RG \
  --lb-name lab-vmssLB --name http \
  --backend-pool-name lab-vmssLBBEPool \
  --frontend-ip-name loadBalancerFrontEnd \
  --protocol tcp --frontend-port 80 --backend-port 80

# 3. Allow port 80 through the scale set's NSG
NSG=$(az network nsg list -g $RG --query "[?contains(name,'vmss')].name | [0]" -o tsv)
az network nsg rule create -g $RG --nsg-name $NSG \
  --name allow-http --priority 1010 \
  --destination-port-ranges 80 --access Allow --protocol Tcp

# 4. Test through the load balancer a few times
LBIP=$(az network public-ip show -g $RG -n lab-vmssLBPublicIP --query ipAddress -o tsv)
for i in 1 2 3 4 5 6; do curl -s http://$LBIP; echo; done

The responses show two different hostnames, which means the load balancer is spreading requests across both instances.

If az network nsg list returns nothing, the scale set has no NSG of its own; the subnet's NSG name will show in az network nsg list -g $RG -o table.

# 5. Add autoscale: keep 2–3 instances, scale on CPU
VMSSID=$(az vmss show -g $RG -n lab-vmss --query id -o tsv)
az monitor autoscale create -g $RG --resource $VMSSID \
  --name lab-autoscale --min-count 2 --max-count 3 --count 2
az monitor autoscale rule create -g $RG --autoscale-name lab-autoscale \
  --condition "Percentage CPU > 70 avg 5m" --scale out 1
az monitor autoscale rule create -g $RG --autoscale-name lab-autoscale \
  --condition "Percentage CPU < 30 avg 5m" --scale in 1

# 6. Load the CPU on every instance for 10 minutes
az vmss run-command invoke -g $RG -n lab-vmss \
  --command-id RunShellScript \
  --scripts "nohup timeout 600 sh -c 'yes > /dev/null' >/dev/null 2>&1 &"

# 7. Watch the instance count (run every minute or two)
az vmss list-instances -g $RG -n lab-vmss --query "[].name" -o tsv

After 5–10 minutes a third instance appears, and in the portal the scale set's Scaling → Run history shows the scale-out event. About 5–10 minutes after the load stops, it scales back in to 2.

If az vmss run-command isn't available in your CLI version, run the same command on each instance with az vm run-command invoke -g $RG -n <instance-name> ..., using the names from step 7.

This lab runs 2–3 VMs plus a load balancer and public IP. Delete it when you're done: az vmss delete -g $RG -n lab-vmss, or wait for the full cleanup in section 10.

Part 2 · PaaS

5. Azure App Service

Azure App Service hosts web applications, REST APIs and mobile back ends without you managing any servers. You push code in .NET, Java, Node.js, Python or PHP (or a container image) and App Service runs it, patches the OS and runtime, and gives you HTTPS, custom domains, deployment slots, authentication and autoscale as built-in features.

Key concepts

TierGood forNotable features
Free (F1)Learning and demosShared compute, daily CPU limit, no custom domain TLS, no scale-out
Basic (B1–B3)Low-traffic apps, dev/testDedicated instances, custom domains with TLS, manual scale
Standard (S1–S3)ProductionAutoscale, deployment slots, daily backups
Premium v3 (P0v3–P5mv3)Busy production appsMore slots, faster hardware, zone redundancy
Isolated v2Strict complianceRuns in an App Service Environment inside your own VNet
  • Deployment slots are live copies of your app with their own URL. Deploy to staging, test it, then swap it into production with no downtime; swap back if something breaks.
  • Deployment options: ZIP deploy, GitHub Actions, Azure DevOps, local Git, or a container image from a registry.
  • You pay for the plan, not per app. An empty Standard plan still costs money until you delete it.

Lab 3: Deploy a Python web app on the Free tier

Goal: create a tiny Flask app, deploy it to App Service with one command, change an app setting and stream the logs. Time: about 15 minutes.

# 1. Write a minimal Flask app
mkdir -p ~/lab-webapp && cd ~/lab-webapp
cat > app.py <<'EOF'
import os
from flask import Flask
app = Flask(__name__)

@app.route("/")
def home():
    greeting = os.environ.get("GREETING", "Hello")
    return f"<h1>{greeting} from Azure App Service</h1>"
EOF
echo "flask" > requirements.txt

# 2. Create the plan and app, build and deploy in one step
WEBAPP=lab-web-$SUFFIX
az webapp up --name $WEBAPP --resource-group $RG \
  --location $LOCATION --runtime "PYTHON:3.12" \
  --sku F1 --plan lab-plan

# 3. Open it
URL=https://$(az webapp show -g $RG -n $WEBAPP --query defaultHostName -o tsv)
curl $URL

The page shows Hello from Azure App Service. In the portal, App Services → your app → Overview shows the plan lab-plan on the F1 tier.

# 4. Change configuration without redeploying
az webapp config appsettings set -g $RG -n $WEBAPP --settings GREETING="Namaste"
sleep 30; curl $URL      # app restarts and now says "Namaste from Azure App Service"

# 5. Stream the live logs (Ctrl+C to stop), then refresh the page in a browser
az webapp log config -g $RG -n $WEBAPP --docker-container-logging filesystem
az webapp log tail -g $RG -n $WEBAPP

# 6. Redeploy after a code change: edit app.py, then run from the same folder
az webapp up

Try next (paid): scale the plan to S1 with az appservice plan update -g $RG -n lab-plan --sku S1, create a slot with az webapp deployment slot create -g $RG -n $WEBAPP --slot staging, deploy a change there and use az webapp deployment slot swap. Scale back to F1 or delete the plan straight after.

Part 3 · Serverless

6. Azure Functions

Azure Functions runs small pieces of code in response to events, with no servers to manage and, on the serverless plans, billing only while code runs. A function wakes up when a trigger fires, such as an HTTP request, a timer, a new file in Blob Storage or a message on a queue. It can read and write other services through bindings without writing connection code.

Hosting plans

PlanHow it scales and billsUse it when
Flex ConsumptionServerless, scales out fast (up to 1,000 instances) and to zero, pay per execution. Instance memory of 512 MB, 2 GB or 4 GB; optional always-ready instances; VNet integration. Linux only.The default for new serverless apps
PremiumPre-warmed instances so there's no cold start, bigger instances, VNet support, billed per instance.Steady traffic, strict latency
Dedicated (App Service plan)Runs on an App Service plan you already pay for.You have spare App Service capacity
Container AppsFunctions packaged as a container inside a Container Apps environment.Functions alongside other microservices, GPUs
Consumption (legacy)The original pay-per-execution plan. Microsoft now calls it legacy and recommends Flex Consumption for new apps; hosting on Linux in this plan retires on 30 September 2028.Existing Windows apps only
  • Cold start: when an app has scaled to zero, the first request waits while an instance starts. Always-ready instances (Flex) or the Premium plan remove that delay at extra cost.
  • Durable Functions adds stateful workflows (chaining, fan-out/fan-in, human approval) on top of normal functions.
  • Every function app needs a storage account for its internal state and deployment package.

Lab 4: An HTTP-triggered Python function on Flex Consumption

Goal: create a function app on the Flex Consumption plan, write an HTTP function, publish it and call it. Time: about 20 minutes.

This lab uses the Azure Functions Core Tools (func). Run func --version in Cloud Shell to check they're there; on your own machine, install them from Microsoft's Functions documentation first.

# 1. Check Flex Consumption is offered in your region
az functionapp list-flexconsumption-locations --query "sort_by(@,&name)[].name" -o tsv | grep -x $LOCATION \
  || echo "Pick another region from the list above"

# 2. Storage account (lowercase letters and numbers only, 3–24 chars)
FNSTORE=labfnst$SUFFIX
az storage account create -g $RG -n $FNSTORE -l $LOCATION \
  --sku Standard_LRS --allow-blob-public-access false

# 3. Function app on Flex Consumption (also creates Application Insights)
FNAPP=lab-fn-$SUFFIX
az functionapp create -g $RG -n $FNAPP \
  --storage-account $FNSTORE \
  --flexconsumption-location $LOCATION \
  --runtime python --runtime-version 3.11

# 4. Create the project and an HTTP function locally
mkdir -p ~/lab-func && cd ~/lab-func
func init . --worker-runtime python
func new --name hello --template "HTTP trigger" --authlevel anonymous

# 5. Publish to Azure (dependencies are built remotely)
func azure functionapp publish $FNAPP

# 6. Call it
FNHOST=$(az functionapp show -g $RG -n $FNAPP --query defaultHostName -o tsv)
curl "https://$FNHOST/api/hello?name=Nithin"

The response is Hello, Nithin. This HTTP triggered function executed successfully. In the portal, open the function app → Monitoring → Invocations or Application Insights → Live metrics, call the URL again, and watch the request arrive.

Try next: add a timer function with func new --name heartbeat --template "Timer trigger", set its schedule to 0 */5 * * * * (every five minutes), publish again and watch the logs. Then open function_app.py to see how the trigger is declared as a Python decorator.

Part 4 · Containers

7. Containers in Azure

A container packages an application with everything it needs (runtime, libraries, config) into one image that runs the same way on any host. Containers start in seconds and use far less overhead than VMs because they share the host's kernel. Azure has three main places to run them, plus a registry to store the images.

Container InstancesContainer AppsAKS
What it isRun a container directly, billed per secondServerless container platform built on Kubernetes, KEDA and Dapr, with the cluster hiddenManaged Kubernetes cluster; Azure runs the control plane, you run the nodes
ScalingNone built in; you start more instancesAutomatic on HTTP, CPU, queue length or events; scale to zeroHorizontal Pod Autoscaler and cluster autoscaler, configured by you
Kubernetes APINoNoYes, full kubectl access
Good forBatch jobs, build agents, quick testsAPIs, web apps, background workers, event processingLarge platforms, custom operators, teams that need Kubernetes itself
Cost modelvCPU and memory per secondConsumption: per vCPU-second, GiB-second and request, with a monthly free grantControl plane free on the Free tier (paid Standard tier adds an SLA); you pay for node VMs

Azure Container Registry (ACR) is a private Docker-compatible registry in your subscription. It comes in Basic, Standard and Premium tiers (Premium adds geo-replication and private endpoints), can build images in the cloud with az acr build, and connects to AKS, Container Apps and App Service through managed identity.

Lab 5a: Run a container in seconds with Container Instances

Goal: run Microsoft's sample web container with a public DNS name, read its logs, then delete it. Time: about 10 minutes.

# 1. Register the provider once per subscription (safe to re-run)
az provider register --namespace Microsoft.ContainerInstance --wait

# 2. Create the container group
az container create -g $RG --name lab-aci \
  --image mcr.microsoft.com/azuredocs/aci-helloworld \
  --os-type Linux --cpu 1 --memory 1.5 \
  --ports 80 --ip-address Public \
  --dns-name-label lab-aci-$SUFFIX

# 3. Get its address and test
ACIFQDN=$(az container show -g $RG -n lab-aci --query ipAddress.fqdn -o tsv)
curl -s http://$ACIFQDN | head -20

# 4. Logs and a shell inside the container
az container logs -g $RG -n lab-aci
az container exec -g $RG -n lab-aci --exec-command "/bin/sh"   # type exit to leave

# 5. Delete (ACI bills per second while running)
az container delete -g $RG -n lab-aci --yes

Opening http://<fqdn> in a browser shows the "Welcome to Azure Container Instances" page, and az container logs shows your request.

Lab 5b: Deploy a scale-to-zero app with Container Apps

Goal: deploy a container app with public HTTPS ingress, set scale rules from 0 to 5 replicas, and watch it scale. Time: about 20 minutes.

# 1. CLI extension and providers (once)
az extension add --name containerapp --upgrade
az provider register --namespace Microsoft.App --wait
az provider register --namespace Microsoft.OperationalInsights --wait

# 2. Create the environment and the app in one command
az containerapp up --name lab-ca \
  --resource-group $RG --location $LOCATION \
  --environment lab-ca-env \
  --image mcr.microsoft.com/k8se/quickstart:latest \
  --target-port 80 --ingress external

# 3. Get the HTTPS URL
CAURL=https://$(az containerapp show -g $RG -n lab-ca --query properties.configuration.ingress.fqdn -o tsv)
curl -s $CAURL | head -5

# 4. Allow scale to zero, up to 5 replicas, 20 concurrent requests per replica
az containerapp update -g $RG -n lab-ca \
  --min-replicas 0 --max-replicas 5 \
  --scale-rule-name http-rule --scale-rule-type http \
  --scale-rule-http-concurrency 20

# 5. Generate load for about 60 seconds, then count replicas
for i in $(seq 1 3000); do curl -s -o /dev/null $CAURL & done; wait
az containerapp replica list -g $RG -n lab-ca --query "[].name" -o tsv

Under load the replica list shows more than one replica. Leave it idle for a few minutes and run the replica command again: it drops to zero, and the next request to the URL starts a new replica.

Also look at Revisions and replicas in the portal. Each update created a new revision, and you can split traffic between revisions for blue-green or canary releases.

Lab 5c (optional, paid): A one-node AKS cluster

Goal: create the smallest practical AKS cluster, deploy nginx with kubectl, expose it with a load balancer and delete the cluster the same day. Time: about 25 minutes.

The AKS control plane is free on the Free tier, but the node VM, its disk, the load balancer and the public IP are billed against your credit while the cluster exists. Don't leave it running overnight.

# 1. Create a 1-node cluster on the Free tier
az aks create -g $RG -n lab-aks \
  --tier free --node-count 1 --node-vm-size Standard_B2s \
  --generate-ssh-keys

# 2. Connect kubectl (already installed in Cloud Shell)
az aks get-credentials -g $RG -n lab-aks --overwrite-existing
kubectl get nodes

# 3. Deploy, scale and expose nginx
kubectl create deployment web --image=nginx --replicas=2
kubectl expose deployment web --port=80 --type=LoadBalancer
kubectl get pods -o wide
kubectl get service web --watch      # wait for EXTERNAL-IP, then Ctrl+C

# 4. Test, then scale the deployment
curl http://<EXTERNAL-IP>
kubectl scale deployment web --replicas=4 && kubectl get pods

# 5. Delete the cluster (also removes its MC_ node resource group)
az aks delete -g $RG -n lab-aks --yes --no-wait

The nginx welcome page loads from the external IP, and kubectl get pods shows four running pods after the scale command.

AKS creates a second resource group named MC_compute-lab-rg_lab-aks_<region> for the node VMs and networking. Look at it in the portal, but don't change it by hand; AKS manages it, and it's removed when you delete the cluster.

8. Which one should I use?

Ask these questions in order and stop at the first "yes":

ScenarioBest fitWhy
Move an on-prem Oracle 19c server as isVirtual MachinesNeeds the OS, custom kernel parameters and installed software
Web servers for a sale that gets 10× traffic for one weekVM Scale SetsAutoscale identical VMs behind a load balancer
Company website in .NET or Python, deployed from GitHubApp ServiceManaged runtime, slots for safe releases, custom domain and TLS
Resize every image uploaded to Blob StorageFunctionsEvent-driven, runs for seconds, pay only per upload
Nightly data export job in a containerContainer InstancesStart, run, stop; billed per second

9. Real-world design: an online pharmacy

Here's how one product, an online pharmacy for a hospital group, could use five of these services together. Each service is picked for the job it does best:

  • App Service runs the storefront. Releases go to a staging slot first and are swapped in after a smoke test.
  • Container Apps runs the order, catalog and payment APIs as separate microservices. They scale on HTTP traffic during the day and drop to one replica (or zero for the catalog importer) at night.
  • Functions sends an SMS when an order message lands on a Service Bus queue, and a timer function starts the nightly report.
  • Container Instances runs the nightly report job for about 15 minutes and then stops, so it costs only those 15 minutes.
  • Virtual Machines host the old inventory database, which the vendor only supports on a specific OS version. It sits in an availability zone pair with backups to a Recovery Services vault.

No AKS here, because the team has no need for the Kubernetes API itself. If they later grow to a platform team running dozens of services with Helm charts and custom operators, that's when AKS becomes the right call.

10. Clean up

Everything from every lab lives in one resource group, so one command removes it all, including the VMs, disks, load balancer, plans, function app, storage account and container apps. If you created the AKS cluster, its MC_ resource group is removed along with the cluster.

az group delete --name compute-lab-rg --yes --no-wait

# Confirm it's gone after a few minutes
az group exists --name compute-lab-rg     # false

Also check Cost Management → Cost analysis the next day to confirm that nothing kept running.

12. Key takeaways

  • Virtual Machines give full control of the OS. Remember to deallocate, not just shut down, to stop compute charges.
  • Scale Sets run many identical VMs with autoscale and a load balancer; Flexible orchestration is the default for new ones.
  • App Service runs web apps and APIs on a managed platform. You pay for the plan, and slots give zero-downtime releases from Standard tier up.
  • Functions run event-driven code with triggers and bindings. Use Flex Consumption for new serverless apps.
  • Containers: ACI for a quick or one-off container, Container Apps for serverless microservices that scale to zero, AKS when you need Kubernetes itself. ACR stores the images.
  • Moving from VMs toward Functions, you manage less and get less control, so pick the most managed service that still meets the requirement.
