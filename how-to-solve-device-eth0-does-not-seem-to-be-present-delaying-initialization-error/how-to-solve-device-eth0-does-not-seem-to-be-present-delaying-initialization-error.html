How to Solve "Device eth0 does not seem to be present, delaying initialization"

By Sunke Nithin · July 11, 2019   LinuxLinuxNetwork

After cloning an Oracle Linux 6 VM in VMware, the clone had no network: ifconfig showed only the loopback interface, and restarting the network failed with "Device eth0 does not seem to be present, delaying initialization". The cause is the cloned MAC address.

The Symptom

BASH
# ifconfig
lo   Link encap:Local Loopback
     inet addr:127.0.0.1  Mask:255.0.0.0
     ...

# service network restart
Bringing up interface eth0:  Device eth0 does not seem to be present, delaying initialization.

The interface configuration looked fine:

CONF
DEVICE=eth0
TYPE=Ethernet
ONBOOT=yes
BOOTPROTO=none
HWADDR=08:00:27:DC:33:3F        # <-- the OLD VM's MAC address
IPADDR=192.168.1.150
NETMASK=255.255.255.0
GATEWAY=192.168.1.1
NM_CONTROLLED=no
USERCTL=no

Why It Happens

When a VM is cloned, the hypervisor gives the new VM a new MAC address. But on RHEL/OL 6 the clone still has:

  • /etc/udev/rules.d/70-persistent-net.rules, which maps the old MAC address to the name eth0 — so the new NIC is named eth1 instead;
  • HWADDR= with the old MAC in ifcfg-eth0, so the config doesn't match any present device.

The Fix

BASH
# 1. see the real MAC address of the new NIC
ip link            # or: ifconfig -a

# 2. forget the old MAC-to-name mapping
rm -f /etc/udev/rules.d/70-persistent-net.rules

# 3. update or remove HWADDR (and remove UUID if present) in the config
vi /etc/sysconfig/network-scripts/ifcfg-eth0

# 4. reboot (udev regenerates the rules file with the new MAC as eth0)
reboot

After the reboot, the NIC comes up as eth0 with its address.

Prevent it: before turning a VM into a template, delete 70-persistent-net.rules and remove HWADDR/UUID from the ifcfg files. On RHEL/OL 7 and later the persistent rules file is gone (interfaces get predictable names like ens33), but a hard-coded HWADDR can still cause the same problem.
