How to Migrate a SQL Server 2016 Database to Oracle 19c Using SQL Developer

By Sunke Nithin · April 11, 2025   DatabaseOracleMSSQLMigration

Oracle SQL Developer's Migration Wizard moves a whole SQL Server database to Oracle: it captures the source model, converts data types, translates T-SQL objects to PL/SQL, generates the Oracle schema and moves the data. Here I migrate a small SQL Server 2016 database, imagedb, into an Oracle 19c PDB.

ComponentDetail
SourceSQL Server 2016 (13.0.5026), database imagedb
TargetOracle Database 19c, PDB ncdb
ToolOracle SQL Developer (latest), on Windows
DriverjTDS JDBC driver (jtds-1.3.1.jar)
AccountsSQL Server login with read access; an Oracle DBA account for the target
For copying just one table, the right-click Copy To Oracle is quicker — see Migrating a table from SQL Server to Oracle.

1Sample Source Data

A table holding images as binary data, with 11 rows:

2Add the jTDS Driver

Tools → Preferences → Database → Third Party JDBC Drivers → Add Entry, select jtds-1.3.1.jar (from SourceForge), and restart SQL Developer:

3Connect to SQL Server

Create a connection of type SQLServer: host, port 1433, login, then Retrieve database and choose the database. (TCP/IP must be enabled in SQL Server Configuration Manager.)

4Create the Migration Repository

SQL
-- in the target PDB, as a DBA
CREATE USER mig_repo_schema IDENTIFIED BY "<password>"
  DEFAULT TABLESPACE users QUOTA UNLIMITED ON users;
GRANT CONNECT, RESOURCE, CREATE SESSION, CREATE VIEW, CREATE MATERIALIZED VIEW
   TO mig_repo_schema;

Connect as that user, then Tools → Migration → Repository Management → Create Repository:

5Run the Migration Wizard

Right-click the SQL Server database and choose Migrate To Oracle:

Choose the repository, then a project name and an output directory for the generated scripts:

Pick the source connection (online mode) and the database to capture:

Review the data type mappings — e.g. IMAGE → BLOB, DATETIME → DATE, INT → NUMBER(10,0) — and the object types to translate:

Choose the target connection (I used SYSTEM on the PDB, because the wizard creates a new user for the schema) and the data move connections:

Online mode moves the data directly over JDBC — fine for small databases. For large ones, choose offline: the wizard generates scripts that export with BCP and load with SQL*Loader.

6Check the Result

The wizard created a user named after the source database — IMAGEDB — expired and locked. Unlock it and set a password:

SQL
ALTER USER imagedb IDENTIFIED BY "<password>" ACCOUNT UNLOCK;

-- compare with SQL Server: SELECT COUNT(*), SUM(DATALENGTH(ImageData)) FROM dbo.ImageStore;
SELECT COUNT(*), SUM(DBMS_LOB.GETLENGTH(imagedata)) FROM imagedb.imagestore;

EXEC DBMS_STATS.GATHER_SCHEMA_STATS('IMAGEDB');

Connect as the new user and check the data — all 11 rows arrived:

Tips

  • Run the migration in a test environment first and review the generated scripts.
  • Check translated procedures and triggers carefully — T-SQL to PL/SQL translation is never 100%.
  • For large databases, migrate in parts and use offline data movement.
  • Make sure you're licensed for both products in production.
