The Database Writer Process (DBWn) in Oracle

By Sunke Nithin · October 29, 2020   DatabaseOracle

Every change to a table or index happens first in memory, in the database buffer cache. The database writer background process (DBWn) is what eventually puts those changed blocks into the data files on disk. Knowing when and why it writes explains a lot about checkpoints, instance recovery and some common wait events.

Dirty, Clean and Cold Buffers

  • A buffer becomes dirty when a session changes the block in it; the copy on disk is now out of date.
  • A cold buffer is one that hasn't been used recently (by the cache's least-recently-used logic); a hot one is in frequent use.
  • Sessions reading a block from disk need a free (clean, reusable) buffer to put it in.

DBWn's main job is to write cold, dirty buffers so they become clean and reusable, while hot blocks — small lookup tables, index root blocks — stay in memory. Commits don't depend on DBWn: a commit only waits for LGWR to write the redo (see Log Writer Process (LGWR)). Dirty blocks can stay in the cache long after the commit; redo protects them.

When DBWn Writes

  • Free buffers run short — a server process scans a threshold number of buffers without finding a free one and signals DBWn, which writes dirty buffers asynchronously.
  • Checkpoints — DBWn keeps writing the oldest dirty buffers so the checkpoint position (where instance recovery would start in the redo) moves forward. FAST_START_MTTR_TARGET controls how aggressively.
  • Other events — e.g. a tablespace taken offline or put in backup mode, or a segment dropped/truncated, need its blocks written first.

DBWn always writes in batches (multi-block writes) for efficiency; the batch size depends on the platform.

How Many Writers?

DB_WRITER_PROCESSES sets the number. One writer (DBW0) is enough for most systems; additional ones help write-heavy databases on multi-CPU servers. Names run DBW0–DBW9, DBWa–DBWz, then BW36–BW99 — up to 100 writers in 12c and later (20 in older releases). If you don't set it, Oracle chooses a value from the CPU count.

SQL
show parameter db_writer_processes

-- the writers running now (DBW0, DBW1 ... or BWnn above 36)
select pname, spid from v$process where pname like 'DBW%' or pname like 'BW%' order by pname;

-- signs DBWn can't keep up
select event, total_waits, time_waited_micro/1e6 secs
from   v$system_event
where  event in ('free buffer waits','write complete waits','db file parallel write');
SQL
alter system set db_writer_processes=4 scope=spfile;   -- static: needs a restart
Before adding writers, check that the operating system supports asynchronous I/O for your data files (DISK_ASYNCH_IO, FILESYSTEMIO_OPTIONS=SETALL on file systems). With async I/O, one writer can often do the work of several. Frequent free buffer waits usually point to slow storage or a too-small buffer cache rather than too few writers.
