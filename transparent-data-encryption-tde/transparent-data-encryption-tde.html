Transparent Data Encryption (TDE) in Oracle Database

By Sunke Nithin · February 5, 2020   DatabaseEncryptionOracle

Oracle Database secures data inside the database with authentication, authorization and auditing — but not the operating-system data files the data is stored in. Transparent Data Encryption (TDE) closes that gap: it encrypts sensitive data in the data files (and therefore in backups), and keeps the encryption keys in a security module outside the database called a keystore.

TDE is transparent because applications don't change. Data is encrypted automatically when it's written to disk and decrypted automatically when an authorized session reads it, and key management is built in. You can encrypt individual columns or entire tablespaces.

1Benefits and How It Works

  • Sensitive data stays encrypted if the storage media or a data file is stolen — including backups shipped to off-site storage.
  • It helps you meet security-related regulatory compliance requirements.
  • Database users and applications see decrypted data as usual; they don't need to know it's stored encrypted.
  • You can encrypt data with zero downtime on production systems (online table redefinition, or online tablespace encryption from 12.2), or offline during a maintenance window.
  • No application changes — the database handles encryption and decryption.

Both column and tablespace encryption use a two-tier key architecture: data is encrypted with table or tablespace keys, and those keys are themselves encrypted with a TDE master encryption key stored in the keystore. Without the master key, an intruder can't read the data from storage or backup media.

2Configure and Create the Software Keystore

The example database is sundev (Oracle 19.3) on host orclncdvl01.

Step 1 — Create the keystore directory

BASH
mkdir -p /d01/app/oracle/admin/sundev/tde_wallet

Step 2 — Tell the database where the keystore is

Add this entry to sqlnet.ora:

SQLNET.ORA
ENCRYPTION_WALLET_LOCATION =
  (SOURCE = (METHOD = FILE)
    (METHOD_DATA =
      (DIRECTORY = /d01/app/oracle/admin/sundev/tde_wallet/)))
ENCRYPTION_WALLET_LOCATION in sqlnet.ora is deprecated from Oracle 19c. The newer method is the WALLET_ROOT and TDE_CONFIGURATION initialization parameters, for example ALTER SYSTEM SET WALLET_ROOT='/d01/app/oracle/admin/sundev/wallet' SCOPE=SPFILE;, restart, then ALTER SYSTEM SET TDE_CONFIGURATION='KEYSTORE_CONFIGURATION=FILE'; — the keystore then lives in a tde subdirectory of WALLET_ROOT.

Step 3 — Create the keystore

Connect as a user with the SYSDBA, SYSKM or ADMINISTER KEY MANAGEMENT privilege, and create the keystore with a password:

SQL
sqlplus / as sysdba

ADMINISTER KEY MANAGEMENT CREATE KEYSTORE '/d01/app/oracle/admin/sundev/tde_wallet/'
  IDENTIFIED BY <keystore_password>;

-- keystore altered.
!ls /d01/app/oracle/admin/sundev/tde_wallet/
-- ewallet.p12

The ewallet.p12 file that appears is the keystore. Check its status:

SQL
SELECT wrl_type, wrl_parameter, status, wallet_type FROM v$encryption_wallet;

3Open the Keystore and Set the Master Key

The keystore status moves through three stages:

CLOSED→ open →OPEN_NO_MASTER_KEY→ set key →OPEN

Open the keystore

SQL
ADMINISTER KEY MANAGEMENT SET KEYSTORE OPEN IDENTIFIED BY <keystore_password>;

Set the TDE master encryption key

SQL
ADMINISTER KEY MANAGEMENT SET KEY
  IDENTIFIED BY <keystore_password>
  WITH BACKUP USING 'master_key_backup';
Multitenant (CDB) databases: run these statements in the root container and add CONTAINER = ALL, so every PDB's keystore is opened and gets a master key.

Open the keystore automatically (auto-login)

A password keystore must be opened again after every restart. To have it open automatically, create an auto-login keystore (cwallet.sso) from it:

SQL
ADMINISTER KEY MANAGEMENT CREATE AUTO_LOGIN KEYSTORE
  FROM KEYSTORE '/d01/app/oracle/admin/sundev/tde_wallet/'
  IDENTIFIED BY <keystore_password>;
Back up the keystore. If you lose ewallet.p12 or its password, the encrypted data can't be decrypted — not even by Oracle Support. Back it up separately from the database backups (keeping them together defeats the point of encrypting the backups), and back it up again every time the master key changes. Use CREATE LOCAL AUTO_LOGIN if the auto-login file should only work on this host.

4Encrypt Columns

Whether you encrypt individual columns or whole tablespaces depends on the data types in the table and the features you use — several features don't support TDE column encryption.

Data types you can encrypt with TDE column encryption

  • BINARY_DOUBLE
  • BINARY_FLOAT
  • CHAR
  • DATE
  • INTERVAL DAY TO SECOND
  • INTERVAL YEAR TO MONTH
  • NCHAR
  • NUMBER
  • NVARCHAR2
  • RAW (legacy or extended)
  • TIMESTAMP (incl. WITH TIME ZONE / WITH LOCAL TIME ZONE)
  • VARCHAR2 (legacy or extended)

Encryption adds overhead to each value, so the maximum size of an encrypted column is smaller than normal:

Data typeMaximum size when encrypted
CHAR1,932 bytes
VARCHAR2 (legacy)3,932 bytes
VARCHAR2 (extended)32,699 bytes
NVARCHAR2 (legacy)1,966 bytes
NVARCHAR2 (extended)16,315 bytes
NCHAR966 bytes
RAW (extended)32,699 bytes

Source: Oracle Database Advanced Security Guide, Table 3-1.

Restrictions on TDE column encryption

Don't use TDE column encryption with:

  • Index types other than B-tree
  • Range scans through an index
  • Synchronous change data capture
  • Transportable tablespaces
  • Identity columns
  • Columns used in foreign key constraints

If any of these apply, use tablespace encryption instead.

Create a table with an encrypted column (default algorithm)

Add the ENCRYPT clause to the column. Without an algorithm, TDE column encryption uses AES192.

SQL
CREATE TABLE emp (
  first_name  VARCHAR2(20),
  last_name   VARCHAR2(30),
  emp_id      NUMBER(5),
  salary      NUMBER(5,2) ENCRYPT
);

DESC emp
-- Name                Null?    Type
-- ------------------- -------- ---------------------
-- FIRST_NAME                   VARCHAR2(20)
-- LAST_NAME                    VARCHAR2(30)
-- EMP_ID                       NUMBER(5)
-- SALARY                       NUMBER(5,2) ENCRYPT

Choose an algorithm, or encrypt without salt

  • ENCRYPT NO SALT — encrypt without salt. Salt makes identical values encrypt differently; you must use NO SALT on a column you want to index.
  • ENCRYPT USING '<algorithm>' — one of AES128, AES192 (default), AES256 or 3DES168.
SQL
CREATE TABLE employee (
  first_name  VARCHAR2(128),
  last_name   VARCHAR2(128),
  empid       NUMBER ENCRYPT NO SALT,
  salary      NUMBER(6) ENCRYPT USING 'AES256'
);

Here empid is encrypted without salt, and both columns use AES256 — all encrypted columns in a table must use the same algorithm.

The original example used 3DES168. It still works, but it's a legacy algorithm; use AES (preferably AES256) for new work.

Save space with NOMAC

By default TDE adds a 20-byte integrity check (MAC) to every encrypted value. 'NOMAC' skips it, which can save significant space and CPU on large tables with many encrypted values:

SQL
CREATE TABLE employee (
  first_name  VARCHAR2(128),
  last_name   VARCHAR2(128),
  empid       NUMBER ENCRYPT 'NOMAC',
  salary      NUMBER(6)
);

5Encrypt a Tablespace

Tablespace encryption encrypts everything stored in the tablespace and avoids the column-level restrictions above. A new encrypted tablespace:

SQL
CREATE TABLESPACE secure_data
  DATAFILE '/d01/app/oracle/oradata/sundev/secure_data01.dbf' SIZE 100M
  ENCRYPTION USING 'AES256'
  DEFAULT STORAGE (ENCRYPT);

From 12.2 you can encrypt an existing tablespace online:

SQL
ALTER TABLESPACE users ENCRYPTION ONLINE USING 'AES256' ENCRYPT;

SELECT tablespace_name, encrypted FROM dba_tablespaces;

6Rekey, Change Algorithms and Passwords

Change the encryption key or algorithm for a table

Each table has one TDE table key for all its encrypted columns. REKEY generates a new key, decrypts the data with the old key, re-encrypts it with the new one and updates the metadata. Add USING to switch algorithm at the same time:

SQL
ALTER TABLE employee REKEY;
ALTER TABLE employee REKEY USING 'AES256';

Change the integrity algorithm

SQL
ALTER TABLE employee REKEY USING 'AES256' 'SHA-1';   -- add/keep the integrity check
ALTER TABLE employee REKEY USING 'AES256' 'NOMAC';   -- remove it

Change the keystore password

SQL
ADMINISTER KEY MANAGEMENT ALTER KEYSTORE PASSWORD
  [FORCE KEYSTORE]
  IDENTIFIED BY <old_password>
  SET <new_password>
  [WITH BACKUP [USING 'backup_identifier']];

After changing the password, recreate the auto-login keystore if you use one, and take a fresh backup of the keystore.
