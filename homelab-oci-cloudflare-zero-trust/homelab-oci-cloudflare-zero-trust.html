Connecting a Proxmox Home Lab and Oracle Cloud (OCI) for Free with Cloudflare Zero Trust

9 November 2026 · Nithin Sunke · Cloudflare Mesh · Cloudflare Tunnel · Access · OCI · Proxmox

What we're building

A private, two-way network between a Proxmox home lab and an Oracle Cloud (OCI) VCN, plus remote access from a laptop or phone — with no open inbound ports, no public IPs on the servers, and ₹0 in licences. Cloudflare's free Zero Trust plan does the heavy lifting:

  • Cloudflare Mesh (formerly WARP Connector) links the two private subnets, site to site.
  • The Cloudflare One Client (formerly WARP) on my laptop and phone reaches both subnets by private IP.
  • A Cloudflare Tunnel (cloudflared) publishes the Proxmox web UI at a real HTTPS URL, protected by Cloudflare Access (email one-time PIN).

This post is my build log: the steps that worked, the errors I actually hit, and how I fixed each one.

Traffic paths once it's done:

  • Home VM ↔ OCI VM: VM → its site's Mesh node → Cloudflare → the other Mesh node → target. Both directions, real source IPs preserved.
  • Laptop (anywhere) → home or OCI: Cloudflare One Client → Cloudflare → that site's Mesh node.
  • Any browser → Proxmox: https://pve.<yourdomain> → Access login → cloudflared → 192.168.1.10:8006.

Why Cloudflare Zero Trust, and what's free

I'd previously linked the same lab to OCI with Tailscale subnet routers. Cloudflare's free tier gives a comparable mesh plus things Tailscale doesn't bundle: public HTTPS publishing for web apps, SSO in front of them, DNS filtering and per-port firewall policies — all from one dashboard.

Limits worth knowing: 24-hour log retention, community support only, and Mesh is still labelled beta. For production database traffic, IPsec or FastConnect remains the standard (see the Data Guard section).

Prerequisites

  • A Cloudflare account and a domain whose nameservers point to Cloudflare. I used a free DigitalPlat (dpdns.org) subdomain — it works, but read Issue 10 below first.
  • An OCI tenancy (Always Free is enough).
  • Proxmox VE with a free static IP on the LAN for the Mesh node.
  • Router access to add static routes, or willingness to add routes on each host.
  • Non-overlapping CIDRs: home 192.168.1.0/24, OCI 10.0.0.0/16, and nothing inside Cloudflare's 100.96.0.0/12.
  • Mesh node sizing (Cloudflare's supported list): Debian 12/13 or Ubuntu 22.04/24.04/26.04 (RHEL 9/10 also listed), 3 vCPU minimum, 4 recommended, 1–2 GB RAM.

Step-by-step build

Step 1 — Cloudflare Zero Trust org

  1. Add your domain to Cloudflare (Free plan) and change its nameservers at the registrar. Wait for Active.
  2. Open Zero Trust, pick a team name (e.g. mylab → mylab.cloudflareaccess.com), choose the Free plan.
  3. Confirm One-time PIN is enabled as a login method.
  4. Team & Resources → Devices → Device enrollment: allow only your email.
  5. Networking → Mesh → Get started: run the wizard. It sets Mesh IPs (100.96.0.0/12), device reachability and the Gateway proxy.
  6. Make sure the Gateway proxy has TCP, UDP and ICMP on, and device profiles use the MASQUE tunnel protocol (Mesh doesn't work on WireGuard).

Step 2 — OCI network and Mesh node

  1. VCN 10.0.0.0/16, a NAT gateway, and a private subnet 10.0.1.0/24 whose route table has 0.0.0.0/0 → NAT gateway.
  2. Security list: ingress from 10.0.0.0/16, 192.168.1.0/24 and 100.96.0.0/12; egress all.
  3. Instance: Ubuntu 24.04 on A1.Flex (4 OCPU / 6 GB, Always Free), private IP 10.0.1.5, no public IP. Reach it via OCI Bastion or the serial console.
  4. VNIC → Skip source/destination check (otherwise OCI drops forwarded packets).
  5. Open Ubuntu's built-in iptables, which rejects forwarded traffic on OCI images:
sudo iptables -I FORWARD 1 -j ACCEPT
sudo iptables -I INPUT 1 -s 192.168.1.0/24 -j ACCEPT
sudo iptables -I INPUT 1 -s 100.96.0.0/12 -j ACCEPT
sudo netfilter-persistent save
  1. Dashboard: Networking → Mesh → Add participant → Add node oci-node → Debian/Ubuntu. Then on the VM:
curl -fsSL https://pkg.cloudflareclient.com/pubkey.gpg | sudo gpg --yes --dearmor -o /usr/share/keyrings/cloudflare-warp-archive-keyring.gpg
echo "deb [signed-by=/usr/share/keyrings/cloudflare-warp-archive-keyring.gpg] https://pkg.cloudflareclient.com/ $(. /etc/os-release && echo $VERSION_CODENAME) main" | sudo tee /etc/apt/sources.list.d/cloudflare-client.list
sudo apt-get update && sudo apt-get install -y cloudflare-warp

printf 'net.ipv4.ip_forward = 1\n' | sudo tee /etc/sysctl.d/99-zzz-cloudflare-warp-connector.conf
sudo sysctl --system

sudo warp-cli --accept-tos connector new <OCI_NODE_TOKEN> && sudo warp-cli --accept-tos connect
warp-cli status      # Connected
Rocky / AlmaLinux instead of Ubuntu? Not on Cloudflare's tested list, but it installs: dnf config-manager --set-enabled crb, dnf install -y epel-release, add https://pkg.cloudflareclient.com/cloudflare-warp-ascii.repo to /etc/yum.repos.d/, dnf install -y cloudflare-warp, and open firewalld (--zone=trusted --add-source=192.168.1.0/24, --zone=public --add-forward).

Step 3 — Home Mesh node in a Proxmox LXC

  1. Create a Debian 12 LXC: 4 cores, 2 GB RAM, static IP 192.168.1.5/24, nesting=1, start at boot.
  2. Give it the TUN device (on the Proxmox host):
pct set <CTID> -dev0 /dev/net/tun        # Proxmox 8.1+
# older: add to /etc/pve/lxc/<CTID>.conf
#   lxc.cgroup2.devices.allow: c 10:200 rwm
#   lxc.mount.entry: /dev/net/tun dev/net/tun none bind,create=file
  1. Inside the container you are root and there is no sudo, curl or gpg — install the basics, then drop sudo from every command:
apt-get update && apt-get install -y curl gpg ca-certificates
curl -fsSL https://pkg.cloudflareclient.com/pubkey.gpg | gpg --yes --dearmor -o /usr/share/keyrings/cloudflare-warp-archive-keyring.gpg
echo "deb [signed-by=/usr/share/keyrings/cloudflare-warp-archive-keyring.gpg] https://pkg.cloudflareclient.com/ $(. /etc/os-release && echo $VERSION_CODENAME) main" > /etc/apt/sources.list.d/cloudflare-client.list
apt-get update && apt-get install -y cloudflare-warp

printf 'net.ipv4.ip_forward = 1\n' > /etc/sysctl.d/99-zzz-cloudflare-warp-connector.conf
sysctl -p /etc/sysctl.d/99-zzz-cloudflare-warp-connector.conf
sysctl net.ipv4.ip_forward     # must print 1

warp-cli --accept-tos connector new <HOME_NODE_TOKEN> && warp-cli --accept-tos connect
ip a show CloudflareWARP        # gets a 100.96.x.x address

Each site needs its own node token; reusing a token makes the second host a replica, not a second site.

Step 4 — Routes and split tunnels (where most of the pain is)

  1. Networking → Mesh → node → Routes: 192.168.1.0/24 on the home node, 10.0.1.0/24 (or the whole 10.0.0.0/16) on the OCI node.
  2. Know which profile your nodes use. Mesh nodes get their own Mesh Network Profile, not the Default device profile. In my account it was in Include mode with only Cloudflare's ranges, so home → OCI traffic never entered the tunnel. Fix it in that profile: either switch it to Exclude mode (and exclude each node's own LAN, see Issue 11) or add the remote subnets to its Include list.
  3. For client devices, edit the profile they use and remove 10.0.0.0/8, 192.168.0.0/16 and 100.64.0.0/10 from Exclude. Keep 169.254.0.0/16.
  4. OCI route table: 192.168.1.0/24 → Private IP 10.0.1.5 and 100.96.0.0/12 → Private IP 10.0.1.5.
  5. Home side: router static routes 10.0.0.0/16 via 192.168.1.5 and 100.96.0.0/12 via 192.168.1.5. On the Proxmox host itself (PVE 9 / Debian 13, ifupdown2) I used:
# /etc/network/interfaces, under iface vmbr0
        post-up ip route replace 10.0.0.0/16 via 192.168.1.5
        post-up ip route replace 100.96.0.0/12 via 192.168.1.5
ifquery -a && ifreload -a      # there is no network.service on PVE 9
ip route get 10.0.1.5          # must say via 192.168.1.5
  1. Test from both ends (-n skips the reverse-DNS noise):
# home LXC
ip route get 10.0.1.5          # should leave via CloudflareWARP
nc -nvz 10.0.1.5 22
# OCI VM
nc -nvz 192.168.1.5 22

Step 5 — Laptop and phone

Install the Cloudflare One Client (Windows/macOS/Linux) or the Cloudflare One Agent app (Android/iOS), log in to your team name with the email PIN, and make sure it's in Traffic and DNS mode. Then ssh / sqlplus straight to 192.168.1.x and 10.0.1.x from anywhere.

Step 6 — Publish Proxmox with Cloudflare Tunnel + Access

  1. Networking → Tunnels → Create a tunnel → Cloudflared, name it homelab.
  2. Install cloudflared on the home LXC (as root, no sudo):
mkdir -p --mode=0755 /usr/share/keyrings
curl -fsSL https://pkg.cloudflare.com/cloudflare-main.gpg -o /usr/share/keyrings/cloudflare-main.gpg
echo 'deb [signed-by=/usr/share/keyrings/cloudflare-main.gpg] https://pkg.cloudflare.com/cloudflared any main' > /etc/apt/sources.list.d/cloudflared.list
apt-get update && apt-get install -y cloudflared
cloudflared service install <TUNNEL_TOKEN>
systemctl status cloudflared
  1. Add a published route: pve.<yourdomain> → https://192.168.1.10:8006, and under Additional application settings → TLS turn on No TLS Verify (Proxmox's certificate is self-signed).
  2. Access controls → Applications → Self-hosted: hostname pve.<yourdomain>, policy Allow → Emails → your address.
  3. Open https://pve.<yourdomain> in a private window: Access PIN page, then the Proxmox login.

Using DNS names instead of IPs

By default the Cloudflare One Client sends every DNS query to Cloudflare Gateway, which only knows public names. IPs work straight away; internal names need one of these:

ApproachHowGood for
Public hostname via TunnelTunnel route pve.<domain> → internal URL, plus an Access appBrowser apps, no client needed
Grey-cloud A recordsCloudflare DNS: A pve.lab → 192.168.1.10, proxy off (DNS only)Quick private names; exposes your internal IP layout publicly (fine for a lab)
Local Domain FallbackDevice profile → Local Domain Fallback: lab.<domain> → your home DNS (Pi-hole/AdGuard/Technitium)Keeping internal records private
Gateway resolver policyDNS policy: domain lab.<domain> → resolve with 192.168.1.53Central management
  • Don't use .local (clashes with mDNS); use lab.<yourdomain> or home.arpa.
  • Some routers and AdGuard/pfSense block public answers that contain private IPs (DNS rebinding protection). If nslookup pve.lab.<domain> 1.1.1.1 works but normal lookups fail at home, whitelist lab.<domain>.
  • A wildcard *.lab pointing at a reverse proxy (Caddy / Nginx Proxy Manager) plus a Let's Encrypt DNS-01 wildcard cert gives valid HTTPS on every internal app.

Best practices

Network design

  • Pick non-overlapping, uncommon CIDRs. 192.168.1.0/24 and 10.0.0.0/16 are the most common ranges on home, hotel and office Wi-Fi; when your laptop sits on such a network, the local LAN wins and that site becomes unreachable. A VLAN like 192.168.50.0/24 and an OCI range like 10.42.0.0/16 avoid this.
  • Advertise only what each node can reach, and prefer specific routes (10.0.1.0/24) over whole VCNs if you plan a hub-and-spoke later.
  • Route the Mesh device range 100.96.0.0/12 back to the local node at each site, not the broader 100.64.0.0/10.
  • Use ip route replace in persistent config, never add … || true.

Security

  • Put an Access application in front of every published hostname; never publish SSH or 1521 publicly — use the client for those.
  • Gateway network policies, top-down: allow your email to the lab CIDRs on the ports you use; allow warp_connector@<team>.cloudflareaccess.com (node-to-node traffic) on DB/SSH ports; block everything else to the lab CIDRs.
  • Tighten OCI security lists from "All" to specific ports once things work.
  • Treat node and tunnel tokens as secrets; delete and recreate a node if one leaks.
  • Only your email in the device-enrollment rule.

Operations

  • Size Mesh nodes to Cloudflare's minimum (3 vCPU); set Start at boot on the LXC — the whole site depends on it.
  • Running cloudflared on the same LXC as the Mesh node works; a separate small LXC makes restarts and troubleshooting independent.
  • After any profile change, run warp-cli disconnect && warp-cli connect and check ip route get <remote IP> — it tells you instantly whether traffic uses CloudflareWARP.
  • Turn on Gateway logging and read Logs → Gateway → Network after each test (free plan keeps 24 h).
  • For HA later, run a second host with the same node token — it becomes a replica.

Can it carry Data Guard and OCI GoldenGate?

Yes, at lab scale. Mesh is plain routed IP in both directions with real source IPs, so both products just see a network between 192.168.1.0/24 and 10.0.0.0/16.

  • Data Guard: redo transport is SQL*Net on 1521. Use ASYNC (SYNC over an internet path slows primary commits), keep MTU at Cloudflare's 1381 and set a sensible SDU; after a node restart, expect gap resolution — good practice for a lab.
  • OCI GoldenGate service: its private endpoint's subnet needs the route 192.168.1.0/24 → 10.0.1.5 and a security rule for 1521 from home; create the connection to the home DB by private IP. Add GoldenGate Microservices ports to the Gateway allow rule if you run on-prem GG too.
  • Where it falls short: throughput is limited by node CPU and home upload; Mesh is beta and each node is a single point of failure. For sustained load or production-like practice, move site-to-site traffic to OCI Site-to-Site IPsec VPN (DRG + Libreswan on Proxmox; needs a public IP that isn't behind CG-NAT) and keep Mesh for people.

Validation checklist

  • Both Mesh nodes Online in Networking → Mesh; warp-cli status = Connected
  • ip route get 10.0.1.5 on the home node leaves via CloudflareWARP
  • Home LXC → OCI: nc -nvz 10.0.1.5 22 open
  • OCI → home: nc -nvz 192.168.1.5 22 open
  • Another home VM → another OCI VM (proves routing and forwarding, not just the nodes)
  • Laptop on mobile data → ssh to a 10.0.1.x and a 192.168.1.x host
  • https://pve.<yourdomain> shows the Access PIN page, then Proxmox
  • A port not in your Gateway allow rule is blocked
  • Reboot both nodes; everything above still passes

Wrapping up

With one free Cloudflare account I now have a home lab and an OCI VCN that talk to each other privately, a Proxmox UI I can open from any browser behind a login, and full private access from my laptop and phone — without a single inbound port. The biggest lessons: check which device profile your Mesh nodes really use, verify routes with ip route get, and never hide a failing command behind || true.
